# ModForge

**Slay the Spire 2 的外置 mod 编辑器。** 可以制作自定义卡牌、真正的增益/减益状态，以及角色皮肤，然后生成一个游戏能正常加载的 mod。

有两个设计选择贯穿整个工具：

- **状态是真的状态。** 因为 ModForge 会生成并编译一个真正的 .NET 程序集，每个状态都是货真价实的 `PowerModel` 子类：会出现在状态栏、叠加层数、按回合衰减，并像原版状态一样与其它卡牌交互。它不是存在卡牌上的近似实现。
- **不靠猜。** 游戏的内容、美术、动画名与二进制格式全部从已安装的游戏里读出来，并在游戏内验证过。`docs/platform-notes.md` 里每一条格式细节都是实测的，不是推测的。

## 环境要求

| | |
|---|---|
| 系统 | Windows（编辑器用系统原生的文件夹选择对话框，所以目标框架是 `net9.0-windows`，且**不需要** WinForms——对话框架直接走 Shell 的 COM 接口） |
| 游戏 | Slay the Spire 2 `v0.107.1`（Steam app `2868840`） |
| .NET | .NET 9 SDK（仅编译 ModForge 本身时需要） |
| Godot | 可选但推荐 —— 见下 |

Godot 用于两件便利的事：

1. **把立绘转成 WebP。** 游戏导出的引擎只带了 WebP 解码器，PNG 负载在运行时会加载失败。ModForge 会调用无头 Godot 无损转换。
2. **提取游戏自带的卡面素材**，让编辑器用真实美术预览卡牌。这些素材以 BC7 压缩存放，普通图片解码器读不了。

如果 Godot 不在 `D:\Tools`，设置环境变量 `MODFORGE_GODOT` 指向它所在目录。没有 Godot 编辑器依然可用，只是需要自备 `.webp` 立绘，预览也会简化。

## 运行

双击 **`ModForge.bat`**。首次运行会编译（之后是增量编译，约一秒），然后启动编辑器并打开浏览器。参数直接透传：

```
ModForge.bat --game "D:\Games\Slay the Spire 2"
ModForge.bat --no-browser
```

或者用命令行：

```
dotnet build ModForge.slnx                            # 编译全部
dotnet run --project src/ModForge.App                 # 自动探测游戏路径
```

编辑器在 `http://127.0.0.1:17890` 打开。整个过程都在本机完成，不需要联网。

端口被占用时会顺延到 17891、17892……这时**以窗口里打印的那一行为准**——浏览器里的旧标签页还
指着 17890，在那儿点什么都会提示"连不上编辑器服务"。`ModForge.bat` 判断"已经在运行"用的是**端口**
而不是进程名，所以重开一次 `ModForge.bat` 只会把 17890 那个打开，不会另起一个副本。

**停止**：关掉 `ModForge.bat` 留下的那个窗口就行。如果窗口找不到了（被别的窗口挡住、最小化、或在另一个桌面上）而进程还占着端口——表现为再点 `ModForge.bat` 却说"已经有一个在运行"、或启动失败——双击 **`StopModForge.bat`**：

```
StopModForge.bat        # 问一句再停，结束前停住等你看结果
StopModForge.bat -y     # 不问、不停留（给脚本或快捷方式用）
```

它会先确认进程在不在，停下来之后再看一眼有没有真的停掉。注意它停不了未保存的内容：编辑器只在按下保存时才写工程，没保存的东西只存在浏览器页面里，停掉就没了——所以它会先问一句（加 `-y` 可跳过）。

⚠️ **两个 `.bat` 必须保持 CRLF 换行**。cmd.exe 解析以裸 LF 结尾的批处理文件时会出岔子，而且症状一点也不像换行问题：注释行里的词会被当成命令去执行（`rem ... the editor` 会试图运行 `the`），检查到某处之后剩下的行会被跳过。实测过一次，表现是启动脚本"构建成功"却报 `Build reported success but  is missing.`——路径变量为空，因为给它们赋值的那几行根本没跑到。改完脚本用 `tools/battest` 确认：

```bash
cd tools/battest && dotnet run
```

## 语言

编辑器有两个独立的语言选择，都在右上角：

| 选项 | 作用 | 影响范围 |
|---|---|---|
| **界面语言** | 编辑器自身的文字 | 按钮、标签、以及**游戏术语**（类型、稀有度、关键词） |
| **内容语言** | 卡牌与状态文本属于哪种游戏语言 | 名称、描述、占位符提示、效果行摘要 |

两者互不干扰：界面设成英文、内容设成中文时，菜单是英文而卡牌文本是中文。

游戏支持 **14 种语言**（`deu eng esp fra ita jpn kor pol ptb rus spa tha tur zhs`）。切到某种内容语言后，名称与描述都会读写该语言的文本；卡牌列表里未翻译的条目会标一个 `·` 提示。

**英语是游戏的兜底语言**：某种语言没填时游戏会显示英语，所以英语必填。导出时英语一定会写出；其余语言只在实际填过时才写。

**游戏术语取自游戏自己的本地化表**，不是在代码里另写一份翻译，所以用词与游戏内一致（攻击 / 技能 / 能力、普通 / 罕见 / 稀有、消耗 / 固有 / 保留 / 奇巧），游戏更新或换语言时也不必改代码。只有 ModForge 自己的概念（如"数值来源"）用自带的双语表。

**按效果自动填充**会按当前内容语言生成句子（不是先写英文再翻译），中文句式用游戏官方译法。

里面填的是**变量占位符**，不是写死的数字——`{Damage:diff()}`、`{CalculationBase:diff()}`、
`{ExtraDamage:diff()}`、`{Repeat:diff()}`。原版卡牌全这么写，好处是升级后卡面文字跟着变、
也才有"提升了多少"的绿字。变量名由槽位规划给出，所以同一张牌上的第二条伤害会写成
`{Damage2:diff()}`，格挡的系数写成 `{CalculationExtra:diff()}`（那个名字与原版的
`ExtraDamage` 不同，是游戏自己埋的坑——写错时游戏内格式化失败）。

编辑器下方那块**效果行摘要**仍然写数字（"对目标造成 4 点伤害。"）：那是给人读的说明，
写成占位符反而难认。两处共用同一份句式表，只有"要不要变量名"这一点不同。

### 语言文件夹（`language/`）

程序里所有"按语言存放的文本"都在这一个文件夹里——界面文案与自动生成描述用的句式各占一块：

```
language/
  ui.js               界面文案（按钮、标签、提示）
  sentences/
    zhs.json          自动生成描述的句式，简体中文
    eng.json          English（兜底：缺哪个语言的文件都回退到它）
```

放在一起是因为它们回答的是同一个问题（"这句话在该语言下怎么说"），分在两个地方时总会有人改错那份。`ui.js` 由 `ui/index.html` 直接引用（服务端为 `/language/` 单开了一条前缀，它是 `ui/` 的兄弟目录，不是它的子目录）。

自动生成描述的句子**不在代码里**，而是按语言放在 `language/sentences/` 里，一种语言一个文件。

每个句式文件分四段：`actors`（自身/目标…）、`sources`（力量/手牌数…）、`words`（手牌/抽牌堆、"升级的"…）、`templates`（整句的句式）。模板里用 `{名字}` 占位，替换是纯文本替换，**不做语法分析**——所以每种语言可以有完全不同的语序：

```jsonc
// zhs.json
"damageOtherCalc": "对{who}造成 等于 {source}{plus} 的伤害。"
// eng.json
"damageOtherCalc": "Deal damage to {who} equal to {source}{plus}."
```

中文把定语放在名词前（"等于 手牌数 + 6 的伤害"），英文放在名词后，同一套模板无法兼顾，只能各写各的——这正是按语言分文件的原因。

**加一种语言**：把 `eng.json` 复制成 `<语言代码>.json` 改掉内容即可，**不必改代码、也不必重新编译**。文件在磁盘上直接生效；程序里另外内嵌了一份同样的文件作为兜底，所以把生成的可执行文件单独拷走也能跑。查找顺序是：

1. 工作目录下的 `language/sentences/`（从仓库根目录启动时就是它，放了文件就优先用，方便自己改）
2. 程序目录向上找到的 `language/sentences/`
3. 程序内嵌的那份

改完文件后**重启编辑器**即可生效（句式表在启动时读入并缓存）。回归检查：

```bash
cd tools/phrasetest && dotnet run          # 打印所有效果形状在每种语言下的说法
cd tools/phrasetest && dotnet run zhs eng  # 只跑指定语言
```

该工具还会检查两种漏项，它们都只会"静默退化成英文"、不会报错：模板里的占位符有没有漏传（漏了会原样打印出 `{name}`），以及用词表是否齐全（取不到时大多有英文兜底，于是中文卡面会突然冒出一句英文）。

## 使用

### 打开时的状态：空工程，只有已重构的效果

**编辑器启动时不载入任何工程，直接从一个空工程开始。** 要继续用某个工程，在「项目」页显式打开
（那里有一个「上次打开的项目」的快捷入口，一键打开）；「新建」给的也是空工程。
这样做有两个原因，都是踩过的：

1. 工程读不进来时（手工改坏文件、或工程里用了已取消的写法），界面看起来一切正常、其实什么都
   没载入——只有日志里有一行。那种状态下用户会以为在编辑自己的工程。
2. 更糟的是接着点「保存」或「导出」——那两个端点都会写盘，把空工程覆盖回工程文件。
   **真丢过两次数据**（第二次删掉了工程里的卡）。

所以第二件事现在有了一道闸：**空工程没有"认领"任何文件夹，这时只允许写进空文件夹**；
工作目录里已经有工程（`About/About.xml` 在）就拒绝写盘，并说清"请先打开它，或另存为新工程"。
「新建 / 打开 / 另存为」成功之后才算认领，之后的保存照常。

界面上也把这件事说清楚：还没认领时，「项目」页写明"现在是一份新建的空项目"，卡牌页的空状态
写明"还没有卡牌……先在「项目」页打开上次的项目"——不写清楚的话，空白的编辑区看起来就像
某个模块（比如描述）丢了。

**效果下拉里列的是全部 30 种。** 效果模块的逐批搬迁已经完成（见「效果模块」一节），
每种效果都由新模块（`Modules/Effects/Kinds/`）提供出码与描述，旧的三处 switch 已删干净。

### 卡牌

卡牌会加入某个角色的牌池，因此出现在该角色的奖励与商店里。编辑器把**卡面预览放在左侧、基本信息放在右侧**，并提供：

- 身份：id、名称、角色牌池、类型、稀有度、目标、费用、**多人游戏卡牌**
- 关键词：消耗、固有、保留、灵巧、永恒、虚无、不可打出
- **效果**：有序列表，是这张卡数值的唯一来源
- **描述**：可用点击式数值标签插入，也可一键生成
- **立绘**：可从游戏本体或本地文件夹里选，预览显示真实卡面

伤害、格挡、施加状态全都是*效果*，不是单独的字段，因此卡面数值由它实际做的事推导而来，不存在两处需要同步的数值。

稀有度会影响出现位置：只有普通、罕见、稀有会进入奖励与商店。若有卡牌永远不会出现，编辑器会提示。

「多人游戏卡牌」那一格按**玩家人数**限制这张牌：选"只在多人合作"就是单人游戏里不出现
（原版那些需要队友的牌就是它），选"只在单人游戏"反之。默认是两种模式都有。
它与「目标」是两件事：这一格管"会不会出现"，目标管"打出去指向谁"——需要队友的牌通常两样都设
（目标选"任意友方"、人数选"只在多人合作"；只设前者的话单人游戏里那张牌会**什么都不做**，
校验器会把这两种情况都提示出来）。

#### 描述

游戏的描述语法（`{Damage:diff()}`）容易写错，写错会在游戏内报错。编辑器把这张卡实际拥有的数值做成按钮，点一下插入到光标处。占位符会跟随效果数值，包括升级。

计算型数值用的是原版的写法：占位符是 `{CalculatedDamage:diff()}`（不是 `{Damage:diff()}`），这一点与游戏自身的卡牌一致。

描述框下方有一块**实时预览**：它按你当前编辑的效果即刻生成描述，改一下就更新，不用先点按钮或校验。点「采用这段」或「按效果自动填充」即可填入；两者填入的内容与预览里看到的完全一致。

### 卡面

点卡牌的「选择卡面」打开选择器，两个来源页签：

| 来源 | 内容 |
|---|---|
| **游戏本体** | 游戏自带的卡图（600+ 张，按角色分组，可搜索）。选一张会取出并复制到**工程的** cardart 文件夹 |
| **本地 cardart 文件夹** | 你自己放在**素材库**（设置里的「卡面路径」，默认程序根目录的 `cardart/`）里的图片，支持子目录与 png / webp / jpg / gif |

两处都在同一个面板里，缩略图即时预览。显示的就是游戏真实卡图（从游戏资源里取出的原始图片，1000×760）。

两个来源落到不同地方，这是有意的：**导入的图属于这份工程**，所以复制进工程的 `cardart/`（保存时也只带用到的那些）；**素材库是你的图**，编辑器只读、从不往里写、也不清理。

选原版卡图时会自动复制一份，之后你可以直接替换项目 cardart 里那个文件来换成自己的画。游戏只认 WebP，所以 PNG 会在生成 mod 时自动转换。

卡面预览的取图按「工程 cardart → 素材库」的顺序找，与保存、导出用的是同一套解析，所以不管图是在工程里还是素材库里，预览都能显示。

### 卡面预览是怎么对齐游戏的

预览不是"看起来像卡牌"，而是照游戏 `scenes/cards/card.tscn` 的实测坐标与 `NCard.Reload` 的绘制逻辑摆的（卡牌 300×422，原点在中心）。几条容易踩的：

| 元素 | 依据 |
|---|---|
| **名字** | 游戏把标签放在 1.66%..14.46%，但绸带贴图里那条**色带**只占图片上部，映射到卡面是 2.31%..10.58%（中线 6.44%）。所以名字按色带中线对齐，而不是按标签框——按框居中的话会明显偏低。先古卡换用另一张绸带，色带中线在 8.19%，名字位置相应下移 |
| **正文** | 描述前关键词、描述、描述后关键词（顺序见 `CardKeywordOrder`）拼成**一段**文字流，和游戏把三者 join 进一个 `RichTextLabel` 一样。行高按游戏的 `line_separation = -3`，但那是减在字体自然行高上（Kreon 是 1.2597em），不是减在字号上 |
| **字号** | 游戏 `MegaRichTextLabel.AdjustFontSize` 会在 12..21 之间二分找一个装得下的字号。预览照做（`fitCardFaces()`），所以长描述会自动缩小，而不是被裁掉 |
| **能量珠** | 图标按牌池选，但游戏 `EnergyColorName` 只有 6 种取值——五个角色名，其余（无色/诅咒/状态/衍生/事件/任务）**一律是 colorless**。数字描边取 `Model.Pool.EnergyOutlineColor`，也是按牌池 |
| **内框 / 绸带 / 类型底片** | 三者都是 `Model.BannerMaterial`，按**稀有度**上色（参数取自 `materials/cards/banners/`）|
| **外框** | 按**牌池**上色（`Model.FrameMaterial`，参数取自 `materials/cards/frames/`）|
| **先古卡** | 立绘铺满全卡、`ancient_card_border` 作外框、`ancient_text_bg_<类型>` 垫在描述后、`ancient_banner` 作绸带；普通的外框/内框/绸带全部隐藏。但**类型牌底片照常显示**（`UpdateTypePlaque()` 是无条件调用的，先古分支只隐藏 `_portraitBorder` / `_portrait` / `_frame` / `_banner`），用与基础卡同一张贴图与同一套配色。PCK 里那张 `card_frame_ancient_s` 在游戏里**没有任何引用**，不要拿它当先古外框 |
| **不能打出的牌** | 不显示费用（游戏里那个位置是"锁"图标）|

牌池与稀有度的着色用的是 CSS 滤镜逼近游戏的 HSV 位移材质，所以颜色是**接近而非逐像素相同**；饱和度与亮度直接对应材质参数，这部分是准的。

### 效果的种类

卡牌能做的事都在「效果」列表里，按顺序执行：

| 类别 | 效果 |
|---|---|
| 数值 | 伤害、格挡、抽牌、获得能量、获得星辰、回复生命、失去生命 |
| 状态 | 施加状态、移除状态（两者都能选"对所有友方 / 某个队友 / 其奥斯提"等，见「作用对象」一节） |
| 牌堆 | 消耗牌（挑哪些牌由选牌器决定，含"消耗这张牌"，也能挑"临时牌集合"里的牌）、复制牌并加入牌堆（同上）、加入指定卡牌（可指定升级版）、丢弃牌堆中的牌、自动打出（牌堆里的牌 / 此牌） |
| 费用 | 降低/提高牌的费用、可以免费打出 |
| 改造 | 升级牌堆中的牌、变化牌堆中的牌（变成随机牌 / 指定牌）、在牌堆间移动牌 |
| 伤害增益 | 使牌的伤害增加（挑哪些牌由选牌器决定，见「让伤害提高」一节） |
| 重放 | 给牌添加重放（挑哪些牌由选牌器决定；另有**卡牌自己的**重放，见「重放」一节） |
| 其它 | 立即执行灾厄判定 |

**移除状态有两种做法、三种对象**：*整个移除*，或者*只减层数*（减 N 层，降到 0 由游戏自己收掉——
界面不写"先减再判 0 再移除"）；对象可以是*指定状态*（下拉里挑，或直接打 id）、*所有正面效果*、
*所有负面效果*。正负由游戏自己的 `TypeForCurrentAmount` 判（就是卡面数值颜色用的同一判据），
所以"当前层数为负"的状态不会判反。选了"整个移除"就没有数值可填：界面把那格置灰，校验器也会
警告"整个移除时写了数值"。施加状态则一直带数值三件套与升级格。

### 作用对象：一个模块管一条轴

每条效果都有一个**作用对象**（界面上叫「作用对象」，原版"对所有敌人造成伤害"里的"所有敌人"
就是这一格）。它的候选、每个候选的**名字**、以及"此刻哪几档可用"，全部由**目标模块**
（`src/ModForge.Core/Modules/Targets/`）回答——界面只照它画，不自己维护任何名单。
以前各效果各写一套，于是同一族效果互相对不上（移除状态比施加状态少三档、回复生命与造成伤害
各少一档，"状态"页里每条效果还都摆出同一套）。

**这套词表覆盖游戏里所有用得上的目标**，分两条轴（作用域）：

| 作用域 | 哪些效果 | 可选的档 |
|---|---|---|
| **造物轴** | 伤害、格挡、回复/失去生命、提高/降低最大生命、施加状态、移除状态、立即执行灾厄判定 | 自身、目标、所有敌人、随机一名敌人、所有友方、随机一名友方、**所有其他友方**、**随机其他友方**、所有人（外加**玩家宠物**那一组四档，见下） |
| **玩家轴** | 获得能量、获得星辰、充能球（生成/激发/栏位）、抽牌、铸造、召唤 | 自身、**任意其他玩家**、所有玩家、随机一名玩家、**所有其他玩家**、**随机其他玩家** |
| **作用于牌** | 消耗牌这类"动牌堆里的牌"的（谁受影响由选牌器决定） | 自身 |

**"友方"含自己、"其他"不含自己**——这是用户定的口径，也是**游戏自己的分法**：

- 原版"所有友方"的牌遍历时**含自己**（`PlayerCreatures` / `c.IsPlayer` 过滤，见 `LegionOfBone` 等 5 张）；
- 而"任意友方"（`TargetType.AnyAlly`）的候选**明确排除自己**——游戏自己的注释就是
  `Targets any ally (any player excluding itself)`。

所以候选里成对出现：含自己的一档（`AllAllies` / `RandomAlly` / `RandomPlayer`）与不含自己的
一档（`AllOtherAllies` / `RandomOtherAlly`）。两轴各自的名字不同：

| 档 | 造物轴 | 玩家轴 |
|---|---|---|
| `AllAllies` | 所有友方（`PlayerCreatures`，**不含宠物**） | 所有玩家（`Players`） |
| `AllOtherAllies` | 所有其他友方 | 所有其他玩家 |
| `RandomAlly` | 随机一名友方（含自己） | —（与"随机一名玩家"同集，所以只列后者） |
| `RandomPlayer` | — | 随机一名玩家（含自己） |
| `RandomOtherAlly` | 随机其他友方 | 随机其他玩家 |
| `Target`（卡牌目标） | 目标（打到的那个生物） | **任意其他玩家**（游戏给它的候选就排除自己） |

随机那一档抽的是"**这一档的全集**"——与"随机一名敌人"从全体敌人里抽是同一个口径，
所以"随机一名友方"含自己、"随机其他友方"不含自己。

**同一档在两轴上的名字不同**，因为两轴落到不同的集合上——所以名字也由模块给：

| 档 | 造物轴 | 玩家轴 |
|---|---|---|
| `Self` | 自身（`Owner.Creature`） | 自身（出牌的那个玩家） |
| `Target` | 目标（打到的那个生物） | **任意一名友方**（选中的那名队友） |
| `AllAllies` | 所有友方（玩家阵营的生物，含宠物） | **所有玩家**（`CombatState.Players`） |
| `RandomAlly` | 随机一名友方 | 随机一名友方（**不含自己**） |
| `RandomPlayer` | —（造物轴上那等于先随机一个人再取生物） | 随机一名玩家（含自己） |

玩家轴给不出"所有敌人"那三档不是偷懒：这几条命令收的是 `Player`（"给谁加能量 / 抽牌"），
而**敌人身上没有 `Player`**——发出来就是一段永远不成立的代码。

**"此刻哪几档可用"是第二层**，由两件事决定，界面与校验器用同一条判据：

- **要"打出时选定的目标"的那两档（「目标」与「目标的奥斯提」）得这张牌真给得出一个合用的对象**。
  造物轴的「目标」要"一个生物"（卡牌目标是任意敌人 / 任意友方都行）；「目标的奥斯提」与
  玩家轴的「目标」要"一名玩家"（只有任意友方给得出）。**用不了时那一档就不显示**，
  而当前值恰好是它时（手改的 JSON、或把卡牌目标改小了）会**列出来并选中 + 下方一句红字**
  说明为什么不可用（"此牌无可选目标。"）。三处的判法不同：卡牌页按这张牌的目标判、
  状态页永远用不了（状态没有出牌目标）、**共享效果页不判**（引用它的卡是什么目标还看不到，
  所以必须能选；校验器在每张引用它的卡上分别判）。
- **玩家宠物**（见下）是**独立的一组目标档**，在界面上单独归进一个「玩家宠物」组。

**两轴各有一套展开**：自己/选定的目标是直接写表达式，一批是 `foreach`，随机是先挑一个再判空。
"随机"走的是游戏自己的随机流（`Rng.CombatTargets.NextItem`，原版取随机目标用的就是它）——
以前那一档其实是 `FirstOrDefault()`，也就是**每次都打第一个敌人**；现在它是真随机。
局部变量按卡内编号起名（`picked0` / `pet0`），两条同类效果在同一张牌上不会撞名。

**玩家宠物（奥斯提）**是**独立的一组目标档**，不是"某一档 + 勾一个取其宠物"：

| 档 | 读作 | 落到谁身上 |
|---|---|---|
| `SelfPet` | 自己的奥斯提 | 出牌者那只（`Owner.Osty`） |
| `TargetPet` | 目标的奥斯提 | 卡牌选中那名玩家的宠物（要牌的目标是**一名玩家**） |
| `AllAlliesPet` | 所有友方的奥斯提 | 每个玩家各一只，**含自己那只**（没宠物 / 不在场的跳过） |
| `RandomAllyPet` | 随机一名友方的奥斯提 | 随机一名玩家的宠物，**含自己那只**（与上一档同一口径："随机"抽的是这一档的全集） |
| `AllOtherAlliesPet` | 所有其他玩家的奥斯提 | 队友的宠物各一次（**不含自己那只**） |
| `RandomOtherAllyPet` | 随机其他玩家的奥斯提 | 随机一名队友的宠物（**不含自己那只**） |

它们**从玩家派生**（宠物是玩家的东西：游戏侧 `Player.Osty` → `PlayerCombatState.GetPet<Osty>()`），
所以"谁"先读成**玩家**、再取那个玩家的 `Osty`；生成物一律带判空（不在场时是 `null`）。
它们**只出现在造物轴的候选里**：宠物是 `Creature`，造物轴的命令（伤害 / 格挡 / 生命 /
施加·移除状态 / 灾厄判定）收它，而玩家轴的命令收 `Player`——"给宠物加能量"在接口上不存在。

**「所有友方 / 随机一名友方」不含宠物**：生成的是 `CombatState.PlayerCreatures`（玩家生物），
与原版一致（原版"所有友方"的牌用 `PlayerCreatures`，见 `LegionOfBone`；"任意友方"的候选也带
`c.IsPlayer` 过滤）。想作用到宠物上就显式选上面那一组——所以"给全队加格挡"不会顺手加给奥斯提。

**状态里没有"打出时选定的目标"**（那是目标那张牌才有的东西）。老工程里这一档是常态
（旧版界面新加的触发默认就是它），所以它按**旧口径**落地：造物轴的效果当作"所有敌人"、
玩家轴的效果当作"自己"；校验器对那种组合给一条提醒（不报错——那会把老工程判成坏的），
状态页的触发行现在有这一格可以改成明确的档（以前它根本没有这一格，只能靠那个隐含口径）。

**"作用于牌"那一轴的隐形目标还没做**：消耗牌这类效果实际是替**某个玩家**动牌堆里的牌
（就是那个"隐形目标"），所以它也该能选"所有玩家 / 随机一名玩家 / 随机一名友方 / 任意一名友方"。
当初搁置的理由（12 条老出码路径要随批 5/6 重写）已经消失——搬迁完成后这条是**目标模块上
剩下的最后一个已知缺口**，做的时候界面与出码都在各行为的 `Kinds/` 文件里，改起来是横切
一遍选牌模块的"作用于牌"轴，不再有"填了不生效"的风险。**卡牌自己的目标**（卡牌页的「目标」）另加了两档，都是原版在用的：**任意友方**（多人合作：
选一个队友）与**所有友方**。游戏的 `AnyPlayer` 与 `TargetedNoCreature`、`Osty` **刻意不收**，
理由都不是"没用"而是"对卡牌不成立"：`CardModel.IsValidTarget` 写死只有"任意敌人 / 任意友方"
能带目标，而 `AnyPlayer` 的语义本要"选一名玩家"，真传了目标反而非法（出牌会被判为非法目标
而取消）；`TargetedNoCreature` 只属于**药剂**（原版只有"污秽药剂"在一个 hack 里用它指商人，
0 张卡用过）；`Osty` 作为**卡牌目标**原版一张卡都没用，而且要表达"打宠物"用效果上的那一项
精确得多（一张牌可以既打敌人又强化自己的宠物）。

**多人游戏卡牌**（卡牌页那一格）对应游戏的 `CardMultiplayerConstraint`，游戏在**卡池与商店**
那一侧按它过滤：标了"只在多人合作"的牌单人游戏里根本不会出现（原版"我相信你""恶魔之盾"这几张
需要队友的牌就是它）。默认档（两种模式都有）不写进文件，所以已有的卡一个字节都不动。

### 临时牌集合：让后面的效果动"刚才那几张牌"

一张牌的效果是**按顺序各自独立**的。"抽 3 张"那条只说抽了 3 张；后面那条"降费"没法指明
"就是刚才那 3 张"——它只能按牌堆或条件挑，而"刚抽到的那 3 张"在牌堆里与别的牌长得一样。

**临时牌集合**就是那个把手：产生牌的效果（抽牌 / 生成 / 挑牌）把那几张牌**存进集合**，
后面的效果把**作用方式**（选牌来源）设成「临时牌集合」并填同一个名字，就能对它们动手。

**键的形状**（一次结算里一个集合唯一）：

```
{局内的牌地址}.{效果编号}.{集合ID}
MYMOD_NEW_CARD#7.3.Drawn
```

- **局内的牌地址** —— 每次出牌结算一个（`TempCardSets.Open(entry)` 发的 `条目#序号`，
  重放的每一遍也各一个）。所以嵌套结算（打出的牌又打出牌）互相看不见对方的集合。
- **效果编号** —— 定义这个集合的那条效果在这张牌的效果列表里是第几条（**1 基**，
  界面上「效果 N」那个号）。读它的效果不需要知道自己的编号，只需要知道"读哪个集合"——
  由模块查出是谁定义的。所以一张牌上**同一个集合 ID 只能定义一次**。
- **集合ID** —— 你自己起的名字（只允许字母、数字、下划线：键用 `.` 分段，带点的 ID 会让
  "按地址前缀清空"误伤别的地址）。

**生命周期是一次出牌结算**：生成代码在 `OnPlay` 开头把地址开出来，结算结束时
（放在 `finally` 里，异常也清）把它下面的集合全部清掉。所以它不会跨牌、跨回合地留着。

**取一个不存在的集合是安全的**（返回空列表，不是 null、不抛异常）：集合很可能不存在——
定义它的那条效果没走到（它在条件分支里、或者牌堆空了没抽到牌）。那是**正常情况**，
用它的效果按"没有牌可动"处理即可。

界面上两处：

- **「临时牌集合ID」**（产生牌的那条效果上，只有真的产出一组牌的效果才有）——填了就把那几张存起来。
- **作用方式 → 临时牌集合**（会挑牌的效果上）——填"取哪个集合"，带下拉建议（本卡已定义的集合，
  不可多选）。**改名会连着改**：把定义那格的名字改掉时，读它的那几条一起改过去。

四个会静默出错的写法由校验器拦（都对不上键）：ID 进不了键、一个 ID 定义两次、
读了本卡上没有的集合、把"存集合"挂在不产牌的效果上。

> **临时牌集合现在对全部会产牌 / 挑牌的效果可用**：
> 写侧是抽牌 / 消耗牌 / 加入指定卡牌 / 复制牌这些产牌与挑牌的种类，读侧是任何用选牌器的
> 效果（把「作用方式」设成「牌集合ID」并填同一个名字）。写侧名单见 `CardSetCatalog.Stores`、
> 读侧判据见 `Reads`——界面、生成器、校验器读的是同一份。

> 生成时只为**用到**集合的工程发那个运行时件（`Runtime/TempCardSets.cs`），而且只有那样
> 的牌才会多出"开地址 + try/finally"这两个结构——不用的牌一个字节都不变。

### 费用：降费与免费是两件事

这两条效果看着像，但游戏里是**两套接口**，作用范围也不同：

| 效果 | 做什么 | 对应接口 | 原版例子 |
|---|---|---|---|
| 降低/提高牌的费用 | 只改**能量**费用，增减 N 点 | `CardEnergyCost.Add*` | 精密瞄准（本回合 −1）、王者之踢（本场战斗 −1）、「沉眠精华」附魔（直到打出 −1） |
| 可以免费打出 | 把能量**与星辰**都清成 0 | `CardModel.SetToFreeThisTurn/Combat` | 子弹时间 |

所以"免费"不是"降很多费"：它会连星辰一起清掉。界面上分成两条，措辞也分开。

两条效果都可以选**挑哪些牌**（选牌器的十步流程：从某几个牌堆里找 / 按某一维筛 / 这张牌自己，
再选全部 / 选择 N 张 / 随机 N 张 / 至多 N 张）与**持续范围**：

- 持续范围：**本回合 / 本场战斗 / 直到被打出**。"直到被打出"只有"降费"有——游戏没有"免费直到打出"这种接口，所以界面上不会给出这个组合（手改的 JSON 会被校验器拦下）。
- "本回合"在游戏里实际是**本回合结束或直到打出**，取先到者；原版所有写"本回合"的降费都是这个语义（这正是 `AddThisTurnOrUntilPlayed` 与 `AddThisTurn` 的差别，后者只用于少数需要跨多次打出一直保持的效果）。

**X 费牌会被跳过**：它没有固定费用可改（原版"子弹时间"也是这么做的）。

**流程九选「选择」时会在打出时弹出选牌界面**，标题是此牌的提示语。这要求 mod 在 `cards` 表里提供 `<卡牌条目>.selectionScreenPrompt`（游戏读的就是这个键，取不到会直接抛异常）——导出时会自动按效果的实际作用生成中英两条提示语（"选择 N 张牌，降低它们的费用"），不必你手写。

「丢弃」生成的是游戏的 `CardCmd.Discard`，不是直接 `CardPileCmd.Add(…, PileType.Discard)`。这个区别是有意的：直接换牌堆不会触发弃牌相关的钩子，于是"被弃掉时"的效果以及一切监听弃牌的卡与状态都不会生效。两者在存档里看起来一样，只有真的打出那张牌才会发现差别。

### 改造牌堆里的牌

两条效果，都用选牌器那套十步流程（与费用类共用）。

**升级牌堆中的牌** —— 对应 `CardCmd.Upgrade`。原版"神化"（升级全部手牌）、"武装"（选择一张升级）用的都是它。

**挑牌时就把不可升级的牌排除掉**（原版"武装"就是这么做的：未升级时用 `FromHandForUpgrade`，升级后是 `Where(c => c.IsUpgradable)`）。不排除的话玩家会白选一张——选完发现什么都没发生。

判据用游戏的 `IsUpgradable`（它会看 `MaxUpgradeLevel`），而不是我们写"是否已升级"这种简化判断，所以**能多次升级的牌**（原版有些诅咒牌如此，mod 也可能）不会被漏掉。

手牌 + 选 1 张时走游戏专门的 `FromHandForUpgrade`：除了过滤，它还会让手牌进入"升级预览"显示模式，与原版完全一致。其它组合用通用的 `FromCombatPile` 加 `c.IsUpgradable` 过滤。

**变化牌堆中的牌** —— 对应 `CardCmd.TransformToRandom` / `TransformTo<T>`，选"变成什么"决定走哪个：

- **变成随机牌**：用游戏自己的变化池，我们不复刻它。池子的规则是**同稀有度**（原版 rare 及以上的牌放宽到 common~rare）、排除自己、战斗中还要求"能战斗中生成"（原版"降灵"变出的"魂"就是战斗中生成的）。照搬接口，池子随游戏版本走。
- **变成指定牌**：可以指定是哪张、以及是不是升级版（对应原版"冲锋！！"：先变成小卒突袭，升级版还会把它升一级）。

不可变化的牌（例如带"永恒"的）会被 `IsTransformable` 过滤掉——游戏对它们会抛异常，所以挑牌时不列出来。

**"变化"与"加入卡牌"是两件事**：变化会把原来的牌替换掉，而三选一（`CardSelectCmd.FromChooseACardScreen`，原版"发现""类星体"用的）是**加入**卡牌用的。原版没有"从三张随机牌里选一张来变化"这种用法。

**在牌堆间移动牌** —— 对应 `CardPileCmd.Add(card, 目标牌堆, 位置)`。原版"头槌"（弃牌堆→抽牌堆顶）、"万事通"（弃牌堆→手牌）、"深挖"（此牌→抽牌堆顶）都是它。

移动**哪些牌**由选牌器的十步流程决定（与其它用选牌器的效果同一套）：

| 流程一 | 移动的是 | 原版例子 |
|---|---|---|
| 从牌堆里找 | 该牌堆里挑出来的牌 | 头槌、万事通 |
| 按牌 ID | 该牌的所有副本 | — |
| 按某一维筛 | 符合条件的牌 | 宇宙冷漠 |
| 这张牌自己 | **这张牌自己** | 深挖 |

早先"搬此牌自己"是独立的一条效果（「将此牌置于牌堆」），与它重叠——两者都是 `CardPileCmd.Add`，只是"搬谁"不同——所以已合并成这一条。流程一选「这张牌自己」时流程九/十都不显示（就这一张），并给出「放入位置」（顶 / 底 / 随机，仅抽牌堆与弃牌堆有意义）。

**消耗牌** —— 对应 `CardPileCmd.Add(card, PileType.Exhaust)`，与上面同构，只是目的地固定是消耗堆（所以没有"移到哪个牌堆"那一格）。

"消耗**哪些**牌"由选牌器决定，与搬运同一套：某个牌堆（"全部"就是整手牌）、按某一维筛、按牌 ID、**这张牌自己**。所以「消耗这张牌」（原版诅咒牌消耗自己）不是单独一条效果，而是它"这张牌自己"那一档——与"搬此牌自己"被吸收进搬运是同一个合并。

"消耗**几张**"是**这条效果自己的数值**（`<base>` 三件套，见「一套选择器」那一节的流程十）：
`<base><count>2</count></base>` 就是"消耗 2 张"，填了来源就是算出来的（"等于星辰"），
填了升级增量就是"升级后多消耗一张"。原因是每个效果的 base 值就是它的基础值，
消耗牌的 base 值就是张数——不需要给选牌器另配一套变量与升级字段。

它**不走弃牌那条路**：`CardCmd.Discard` 会把弃牌的钩子跑完（"被弃掉时"的效果、监听弃牌的卡与状态），而消耗只是把牌挪进消耗堆，两者语义不同。

流程一里**没有卡组**：消耗堆是战斗内的东西，从运行牌库里消耗一张牌没有原版对照，语义也不清楚（战斗结束后那张牌算没了还是回来？）。要"从牌库里永久移除一张牌"，那是另一条效果（原版在商店与事件里做）。

### 一套选择器：十步流程

上面这些"改造一批牌"的效果（降费 / 免费 / 升级 / 变化 / 搬运 / 复制 / 自动打出 / 使牌的伤害增加 /
重放 / 消耗 / 丢弃）共用同一套选择器，界面上就是**十步流程**，字段与流程一一对应
（模型是 `Modules/CardPicking/CardPick.cs`）：

| 流程 | 界面那一格 | 存的是什么 |
|---|---|---|
| 一 | 选择范围 | 此牌 / 牌堆 / 卡组 |
| 二 | 选择牌堆 | 手牌 / 抽牌堆 / 弃牌堆 / 消耗堆，**可多选**；未选择任何牌堆 = 全部战斗牌堆 |
| 一' | 筛选维度 | **多值框**：类型 / 牌 ID / 标签 / 关键词 / 稀有度 / 能量消耗 / 星辰消耗，可同时启用 |
| 四~八 | 该维的取值 | 类型 / 稀有度 / 牌 ID / 标签 / 关键词，**都可多选**（多值之间是"或"） |
| — | 两个费用维度 | 运算符六档单选（不小于 / 不大于 / 大于 / 小于 / 不等于 / X）+ 阈值三件套 |
| 九 | 取牌方式 | 全部 / 选择 N 张 / 随机 N 张 / **至多 N 张** |
| 十 | 张数 | **就是这条效果自己的数值**（它的 `base` 三件套，见下）——消耗牌走这条 |

**筛选是多维度并存的："与"在维度之间，"或"在维度内部。**

        能量消耗 > 2 且 星辰消耗 > 0 且 稀有度 ∈ {稀有, 史诗} 且 类型 ∈ {攻击}

这就是"能量消耗大于 2、星辰消耗大于 0 的稀有攻击牌"那句话的直译（生成出来的谓词见下）。
"启用了哪几维"**不是模型里的一个字段**，而是由内容表达：取值维度看它的列表非不非空，
费用维度看它的运算符是不是"不筛选"。所以"多维并存"没有给工程格式加任何状态，
少一个"开关说启用了、列表却是空的"这种对不上的可能。界面上"启用的维度"本身是一个多值框
（走现成的多值组件 `ui/components.js`），移除一维时会把它的取值/运算符/阈值一起清干净——
否则会留下一条界面上看不见、生成时却还在生效的筛选。

**句子按筛选的复杂程度走两套句式**（判据只有一处：`PickerWording.UseShortForm`）。
中文没有词间空格，所以"形容词栈"只在每段都是单个词时才读得通；一旦同一维有多个取值、
或叠到三个维度以上，就得换成为每个维度点明标签词的从句——否则会念成
`攻击技能能力带「保留」的带「消耗」的打击防御牌`（三处毛病：值粘在一起、关键词各自的"的"
叠起来、整串没有标点）。

| 情况 | 句式 | 例子 |
|---|---|---|
| 每个**取值维度**恰好一个值，且这类维度 ≤ 2 个 | 紧凑（形容词栈） | `能量消耗大于 2 的稀有攻击牌` |
| 同一维多个取值 / 三个取值维度以上 | 显式从句 | `类型为攻击、技能、能力的且带有保留、消耗的且名字中带有打击、防御的且能量消耗不大于 2 的牌` |

判据只数**取值维度**（稀有度 / 类型 / 标签 / 关键词 / 牌 ID），**费用维度不计入**——
它在紧凑写法里就是那个"…的"前缀从句，本来就读得通。显式从句里每个维度各带一个标签词
（`类型为` / `带有…标签的` / `带有` / `名字中带有` / `稀有度为`），从句之间「且」、
同一维的多个取值之间「、」，而**费用从句从最前面挪到最后**（与谓词生成处同一顺序）。
英文对称：紧凑仍是 `Rare Attack cards with energy cost above 2`，显式是
`cards with type Attack, Skill or Power, that have Retain or Exhaust, with energy cost at most 2`。

两套句式共用同一份零件：取值词（`modType*` / `modRarity*` / `modTag*` / `modKeyword*` 存的是
**裸词**）、阈值怎么念（`ThresholdText`）、以及"筛的是哪一维"的顺序。所以切换句式**只改语序与
标签词**，数字与来源的念法不会分叉。关键词是唯一的例外：紧凑写法要用 `modKeywordCompact`
套上「」（"带「消耗」的"），因为裸词直接接名词会被读成"会消耗的牌"。

> 这条判据有个好性质：**紧凑那一侧与旧输出逐字节相同**（每维只有一个值时连接符都用不上），
> 所以切到显式的只有那些本来就念不通的句子。`gensnapshot` 的逐字节 diff 就是这条性质的证明。

**费用维度：运算符在选牌那一侧，阈值在效果那一侧。** 运算符是"怎么比"，住在 `<pick>` 里：

```xml
<pick>
  <source>Piles</source>
  <energyComparison>GreaterThan</energyComparison>
  <starComparison>AtLeast</starComparison>
</pick>
<energyAmount><count>2</count></energyAmount>
<starAmount><count>0</count></starAmount>
```

阈值与 `base` / `repeat` **并列**（`energyAmount` / `starAmount`，各自的 `source` + `coefficient`
就是变量三件套），与数值、次数用的是同一套逐角色读写（见 `Model/ValueRole`）。

**阈值的两个数各占一个变量。** 阈值是"基础值 + 来源 × 变量系数"，与效果数值同一套结构，
所以卡上给**两个**变量（`EnergyAmount` + `EnergyAmountExtra`，同类第二个起加序号——
规划在变量模块的 `ThresholdSlots` 一处），生成的谓词读这两个变量：

```csharp
Cards.Where(c => c.EnergyCost.Canonical > DynamicVars["EnergyAmount"].BaseValue
              + CalcPickEnergy0(cardPlay.Target) * DynamicVars["EnergyAmountExtra"].BaseValue)
```

于是**四项**都同时成立，不必各写一套：升级改基础值、升级改变量系数（`<upgrade>` 里
`energyAmount` 块的 `<count>` 与 `<coefficient>`）、等级表逐级覆盖两者（→ `BaseValue = …`）、
卡面写 `{EnergyAmount:diff()}`（升级后文字跟着变，也有"升了多少"的绿字）。

**来源**（算式的"每单位"那一段）在打出时现算，逐级换算式也支持——"0 级按手牌数、
1 级按弃牌堆数"由生成器按等级分支（与效果数值那边同一个做法）。因为每份取值要有一个
自己的 `player` 局部量，它是发成一个**方法**（`CalcPickEnergy0`）而不是就地铺语句：
同一张卡上可能有多条效果在筛费用，就地铺开会在同一个方法里重复声明而**编译不过**。

界面上只画能生效的格（选了「是 X」时阈值那几格隐去，因为它不比数字）；等级表给"这一级的
能量阈值 / 阈值系数 / 阈值来源"三格。**校验器不再拿阈值系数与来源报警**——它们现在都生效了。

比较的对象是**印在卡面上的费用**：能量读 `CardModel.EnergyCost.Canonical`，星辰读
`CardModel.CanonicalStarCost`（`-1` = 没有星辰费用）。战斗中的降费/加费不影响筛选。
两处有差异，照游戏来：X 费能量卡的 `Canonical` 是 0，所以要筛 X 得用「是 X」那一档；
星辰用「是 X」是因为 X 星辰卡的 `CanonicalStarCost` 仍是 `-1`（`HasStarCostX` 才是它的标志）。

**流程一里没有"按某一维筛"以外的玄机**：模型里现在只有来源（`Source`）一个字段，
筛选是另一组字段（各维取值 + 两个比较器），可以同时存在。顺序不能颠倒——
**流程一决定后面出现哪几格**，排在它前面就会出现"牌堆凭空出现/消失"那种错觉（早先实测过一次）。

**"卡组"= 永久牌库**（`PileType.Deck`），不是全部战斗牌堆：卡组改动是持久的，战斗牌堆不是。
只有卡组能走 `FromDeckForUpgrade / Transformation / Enchantment / Generic` 那一族入口，
它们自带升级 / 变化 / 附魔预览；战斗牌堆走 `FromCombatPile`（单个牌堆）或 `FromSimpleGrid`
（多牌堆 / 带维度筛选时自己拼的候选列表）。

流程二里"未选择任何牌堆 = 全部战斗牌堆"用的是游戏的 `PlayerCombatState.AllCards`，
它含**出牌堆**，比列出来的四个牌堆多一个——原版"完美打击"数所有牌堆里的打击牌用的就是它，
所以这是原版口径，不是疏漏。

（界面上这一页的措辞一律用书面语：参数面板是规格，不是聊天——"挑/找/勾/正好"这类口语改过一次，
见 `language/ui.js` 里那批 `pick*` 文案。）

**显隐跟着"填了会不会生效"走**（不生效的格一律不显示）：

| 选择范围 | 流程二 牌堆 | 筛选维度 | 流程九/十 取法与张数 |
|---|---|---|---|
| 此牌 | 隐去 | 隐去 | 隐去（就这一张，没有"取几张"） |
| 牌堆 | 显示 | 显示 | 显示（"全部"时不显示张数） |
| 卡组 | 隐去 | 显示 | 显示 |

费用维度选「X」时不显示阈值那几格（X 那一档不比数字）；费用筛选**只在会挑牌的效果上**出现，
所以阈值那几格不会在无关的效果上冒出来。三项"填了不生效"的配置由导出时的提示报出来：
非挑牌效果上写了费用阈值 / 有阈值但运算符是"没启用" / 选了 X 又填了阈值。

**比较方式那个下拉里没有「不筛选」**。`CostComparison.None` 是**模型侧的哨兵**——它的意思是
"这一维没启用"，不是"一种比较方式"。而"启不启用"在界面上本来就由上面那个**筛选维度多值框**
表达（框里有它 = 启用），所以下拉只回答"**怎么比**"：不小于 / 不大于 / 大于 / 小于 / 不等于 / 是 X。
把它列进候选的话，用户就能选到一个"选了等于没启用、可那一行还在"的档位——那一行会只剩一个
"不筛选"的下拉，自相矛盾。要停用一维只有一条路：在多值框里把它移除（取值 / 运算符 / 阈值一起清）。

（界面上因此不存在"比较器是没启用却还画着一行"的状态：`filterEnabledDimensions` 里
会话表只管**取值维度**的"刚启用、还没填值"，费用维度的启用与否由比较器本身决定。）

**流程十：张数不是选牌器自己的一套变量，而是效果自己的 `<base>`。**
每个效果的 base 值就是它的基础值，所以消耗牌的 base 值就是"消耗几张"：
`<base><count>1</count><source>HandCount</source><coefficient>0.5</coefficient></base>`
读作"消耗 1 + 手牌数 × 0.5 张"。于是三条能力**自动成立**，不必给选牌器另加一套东西：

- 升级改张数 —— 走 `<upgrade>` 的基础值/系数增量（"升级时张数 +1"，原版"准备就绪"那种）；
- 张数是算出来的 —— 变量由变量模块解析成 `DynamicVars[...]` 或计算结果，选牌器只收结果；
- 描述引用它 —— 固定值时卡面写 `{ExhaustCount:diff()}`（跟着升级变），算出来的把来源念成**张数**
  （"消耗 等于 当前星辰 张牌"，与"抽 等于 手牌数 + 1 张牌"同一句式——量词「张」不能省，
  否则和以"…的牌"结尾的筛选定语链叠成两个"的"，也看不出那串算式是张数）。

哪些效果的张数走这条由策略声明（`CardPickPolicy.CountFromEffect`，目前是消耗牌）。
其余会挑牌的效果（升级 / 变化 / 搬运 / 附魔 / 复制 / 增伤 / 重放 / 降费 / 免费 / 自动打出）的数值
另有含义（复制几份、附几层、打几次…），所以它们的张数仍然写在选牌器自己的那一格
（`<pickCount>`，同样是三件套）；等它们各自整理时再逐条归到"base 即张数"上。

**一个下拉承担"流程一"里的来源与维度**（"此牌 / 按类型 / … / 牌堆 / 卡组"），
但是模型里不再有"维度"字段了——筛选是那一组字段（各维取值 + 两个比较器），见上。

**每条效果能用哪几步由效果自己的策略决定**（`CardPickPolicies.For(kind)`，界面、生成器、导出器、
校验器读的是同一份），所以界面上不会给出这条效果做不到的组合：

| 效果 | 选择范围允许 | 别的限制 |
|---|---|---|
| 消耗牌 / 丢弃牌 | 牌堆、此牌 | **没有卡组**——消耗堆是战斗内的东西，从运行牌库里消耗一张牌没有原版对照 |
| 升级 | 此牌、牌堆、卡组 | 候选中仅包含可升级的牌（`IsUpgradable`） |
| 变化 | 此牌、牌堆、卡组 | 仅包含可变化的牌（`IsTransformable`，"永恒"除外） |
| 附魔 | 此牌、牌堆、卡组 | 仅包含可附魔的牌（`CanEnchant`，含已带有同种附魔的牌） |
| 自动打出 | 牌堆、此牌 | 没有流程九/十（打几张由数值给）；流程二只能选一个牌堆 |
| 其余 | 此牌、牌堆、卡组 | 无 |

七维筛选**每条会挑牌的效果都允许**，所以这一列不必逐条列（`AllDimensions` 一处定义，
要收紧时改那一个数组即可，界面、生成器、校验器跟着变）。

**"张数就是效果数值"的效果（消耗牌）**还多两条显隐规则：流程九选"全部"时整堆都动、
流程一选"这张牌自己"时只有一张，**两种情况下都不读那个数**，所以界面上把张数那三格隐去
（"填了不生效"的格一律不显示）。

描述也会跟着变——同一个"免费"在不同流程一下措辞不同，英文的单复数与大小写都受影响：

> 手牌中所有牌的费用变为 0（本场战斗）。 / ALL cards in your hand cost 0 this combat.
> 使所有防御的费用变为 0（本场战斗）。 / Make every copy of Defend free to play this combat.
> 这张牌的费用变为 0（本场战斗）。 / This card costs 0 this combat.

**带维度筛选时不念牌堆**（筛出来的牌可能散在各个牌堆里），所以张数由条件那一支自己说出来——
"消耗所有攻击牌"与"消耗至多 1 张攻击牌"是两句不同的话，张数说错就等于卡面与生成代码对不上。
张数是算出来的（"等于星辰"）时更进一步：那种情况在游戏里**没有可引用的变量名**
（非伤害/格挡的计算型存在生成类的私有字段里），所以句子把来源念出来当张数
（"至多消耗 等于 当前星辰 张牌"），不写一个看着像真的的数字。

状态上不能用「这张牌自己」（状态没有"这张牌"），「按牌 ID」不填牌名时会报错——两者都由校验器拦下。

**不读旧写法**：枚举里删掉或改过的名字不会做兼容改写——旧文件碰到它们时 `System.Text.Json` 会直接抛异常。这是有意的：静默读成别的值会让效果行为悄悄变掉，比当场报错糟得多。工程读不进来时编辑器会记一条日志、以空工程启动，这样你还能进设置页改路径或换一个工程。

### 自动打出

「自动打出」是一条效果，打出**谁的牌**由选牌器的流程一决定（与「使牌的伤害增加」同一套）：

| 流程一 | 打出的是 | 还要填 | 原版例子 |
|---|---|---|---|
| 从牌堆里找 | 牌堆里**别的牌** | 牌堆（流程二，只能选一个）、打几张（数值那一格） | 浩劫（打出抽牌堆顶并消耗）、横祸（从抽牌堆随机打出 2 张）、狠揍（打出弃牌堆里 3 张随机攻击牌） |
| 这张牌自己 | **这张牌** | 时机（回合开始/结束）+ 牌堆范围 | 轰击（回合开始时若在消耗堆中则将自己打出）、彼岸咆哮（回合结束时若在消耗堆中） |

这一条**没有流程九/十**（打几张由数值那一格给，不是"从牌堆里挑几张"），选「这张牌自己」时数值那一组还会消失——打出的是这张牌本身，没有"打几张"可言；「在哪个牌堆里」也改由时机的**牌堆范围**给出。此时「重复打出次数」仍然有效："若在消耗堆中，将此牌重复打出 2 次"，牌堆条件只判一次、循环里重复打出（打完一次就离开那个牌堆了，每轮重判会导致第二次不触发）。

两条都走游戏自己的 `CardCmd.AutoPlay`，所以被自动打出的牌会照常触发全部效果、遗物与状态，等同于玩家点了那张牌。区别在生成方式：牌堆那条就是普通的打出时语句；「此牌」那条要配「回合开始 / 结束」时机，生成时走引擎为它准备的相位钩子（回合开始 `AfterAutoPrePlayPhaseEnteredEarly`、回合结束 `AfterAutoPostPlayPhaseEntered`）——"自动打出的牌"归引擎的这两个相位管，回合开始时它们是在**抽牌之后**才出来的。

「此牌」不能挂在「打出时」：那会变成打出时再打出自己，无限递归。校验器会拦下缺时机、缺牌堆范围这两种情况（分别会导致递归与误触发），不会让它静默失效。

**立即执行灾厄判定**走 `DoomPower.DoomKill`，让目标当场按灾厄层数判定生死，而不是等到回合末。它对自身没有意义，所以目标只提供单个目标 / 全体敌人 / 随机敌人。

### 数值可以是算出来的

**数值的组成（五个部件，命名要一致）**：

```
数值 = 基础值 + 变量 × 变量系数
        ↑        ↑      ↑
        └────────┴──────┴─ 各自还有"增量"，用于升级：基础值增量 / 变量系数增量
```

| 部件 | 模型字段 | 界面那一格 |
|---|---|---|
| 基础值 | `Amount` | 效果基础值 |
| 变量 | `Source`（`Kind` + 取自谁） | 效果变量来源 / 取自谁 |
| 变量系数 | `Source.PerUnit` | 效果变量系数 |
| 基础值增量 | `Upgrade.AmountDelta` | 升级时效果基础值 + |
| 变量系数增量 | `Upgrade.PerUnitDelta` | 升级时效果变量系数 + |

> 关于「变量」与「来源」：**来源**是把值传给变量的那个东西（手牌数、状态层数…），
> 它本身不属于这条效果；而效果的计算里用到的那个数**就是变量**。界面格子保留"效果"这类定语
> 便于理解，代码里（变量模块内部）一律叫「变量系数」——早先那套「每单位增量」是没改干净的
> 历史遗留，已经清掉。

数值**没有"数值方式"下拉**：给不给「效果变量来源」就决定了它是固定值还是算出来的。

- 来源选「无」→ 固定值，只用「效果基础值」那个数
- 选了来源 → 算出来的，基础值那一段仍然有效（填 0 就是纯粹的"变量 × 变量系数"，例如"每有一张手牌就额外造成 3 点伤害"；要写"造成 5 + 等于力量 的伤害"就填 5）

来源为空时，「取自谁」「效果变量系数」「升级时效果变量系数 +」这几格不会出现——它们只在有来源时才成立。
重复打出次数完全同一套结构：**「重复打出次数来源」选「无」就是固定次数**，选了来源就是算出来的。两处都没有勾选框，也没有第二个"数值方式"下拉；每一格都紧跟在它所升级的那一格后面（基础值 → 它的升级量 → 来源 → 变量系数与它的升级量）。

来源覆盖**状态层数**、生物属性（当前/最大/已损失生命、格挡）、玩家资源（能量、星辰、金币、回合数）、牌堆张数（手牌、抽牌堆、弃牌堆、消耗堆）、**战斗历史计数**（见下），以及**按条件数牌**（"手牌里能量消耗大于 2 的稀有攻击牌有几张"）。

**「状态层数」是一条，不是每个状态一条**：选中它之后紧跟着一格状态选择框，从游戏自带的 250+ 个状态**与本工程自定义的状态**里挑。早先每个原版状态各占一条（力量 / 敏捷 / 中毒……共 18 条），那个列表既长又永远不全——自定义状态与游戏后续新增的都进不去。生成的代码按所选状态取层数（`GetPower<T>()?.Amount`），所以任何状态都能当来源。

**战斗历史计数**都分「本回合 / 本场战斗」两档，全部只数自己维度的事：

| 来源 | 口径 | 原版对照 |
|---|---|---|
| 打出的牌数 | 所有类型 | （多处） |
| 抽到的牌数 | 不含回合开始的起手抽牌 | （多处） |
| 失去生命的次数 | 只数**真的扣到血**的（被格挡挡光的不算，`UnblockedDamage > 0`） | 扯碎 |
| **受击次数** | 所有打到自己身上的伤害事件，**被格挡也算** | —— |
| 攻击次数 | 自己发起的攻击动作（多段攻击算一次；不含奥斯提的攻击） | —— |
| 消耗的牌数 | 牌的主人是自己 | 邪眼、被遗忘的仪式 |
| 弃置的牌数 | 牌的主人是自己 | 铭记死亡 |
| 生成的牌数 | 创建者是自己 | 超大质量体 |
| 受到的伤害 | 掉血部分求和（与"失去生命次数"同一口径） | —— |
| 造成的伤害 | 自己是来源的伤害求和（被格挡不算） | —— |
| 恢复生命的次数 / 恢复的生命量 | 自建计数器（见下一段）；只数**实际恢复**的部分 | ——（原版无数据源） |

**「受击」与「失去生命」的关系**（容易混）：每次掉血必然是一次受击，但被完全格挡的那几下是"受击而没掉血"——所以**受击次数 ≥ 失去生命次数**。要"每被打中一次"用受击，要"每掉一次血"用失去生命。

**恢复生命的次数 / 总量**是自建的：游戏的战斗历史里没有治疗条目，`CreatureCmd.Heal` 也不发战斗钩子，无从查询。所以用到这四个来源时，生成 mod 会附带一个全局计数器（`Runtime/HealTracker.cs`）：用 Harmony 观察 `Creature.HealInternal` 的每一次落地，按生物记下（当时的战斗、回合数、实际恢复量），查询按"同一战斗 + 当前回合数"筛——记账口径模仿原版 `HappenedThisTurn` 的回合戳思路，战斗切换时旧账自动作废。只统计**实际恢复**的部分（满血时的过量治疗不改变生命，不计入）。计数器靠 `Harmony.PatchAll` 挂载，用到这些来源时 `ModEntry` 会自动带上。

**"按条件数牌"用的是与选牌器完全相同的多维筛选**：稀有度 / 类型 / 标签 / 关键词 / 牌 ID / 两个费用维度，维度之间"与"、同一维的多个取值之间"或"——所以"手牌里能量消耗大于 2 的稀有攻击牌有几张"写得出来（生成 `Hand.Cards.Count(c => c.Rarity == Rare && c.Type == Attack && c.EnergyCost.Canonical > 2)`）。它另有一格「从哪个范围数」（手牌 / 抽牌堆 / 弃牌堆 / 消耗堆 / 所有牌堆）。

两处筛的是同一件事，所以**共用同一个谓词生成处**（`CardPickFilter.PredicateOn` 收 `ICardFilter`：选牌那份配置与计数那份筛选都实现它）与同一套界面（界面里六份筛选——选牌一份、计数可能出现在五个位置——都是同一段渲染，只有字段前缀不同）。各写一份的话，迟早出现"这里按标签、那里按类型"这种两边都不报错的偏差。

**唯一的能力差别在阈值**：计数的两个费用阈值是**筛选自己的常数**（谓词写进 `Count(c => …)` 里，lambda 引用不到外面算好的局部变量），所以"能量消耗大于 手牌数 的牌有几张"表达不了——那是选牌那一侧的能力（它的阈值占变量槽、能升级）。计数的阈值只有一格数字，也没有升级增量。

**"战斗历史计数"同样只支持上表那些口径**——按**别人**筛的不行（"你击中该敌人几次"是目标维度；"奥斯提的攻击次数"是另一个生物）。这一档（历史计数）仍是"只数次数、不数类型"：要按条件过滤牌的那种用「按条件数牌」。

**"战斗历史计数"只数得出次数，数不出类型**——例如"本回合打出的牌数"是全体，不是"本回合打出的攻击牌数"。后者要按条件过滤，我们暂时没有对应来源。变量系数支持小数，所以「消耗一半手牌」用 `×0.5` 表达。

**生物属性与状态层数要指明取自谁**：同一个「已损失生命」在自身和目标身上是两个不同的数，所以这些来源旁边有一个 `自身 / 目标` 的选择。效果本身就以自身为目标时（例如"回复等于已损失生命的生命"）这一项不出现——只有一种可能，问了反而多余。牌堆与能量、星辰、金币、回合数属于玩家，不涉及这个选择，界面里也不会给出。

#### 每个效果各占一个变量（一张牌可以有多个同种数值）

**每条带数值的效果各占一个变量槽**。同类里第一个沿用原版名（`Damage` / `Block` / `Summon` /
`StrengthPower`…），后续加序号（`Damage2`、`Damage3`…）。所以一张牌可以有多条伤害、多条格挡、
同一个状态施加多次，**各是各的数值、各升各的**：

```csharp
// "造成 4 点伤害两次，再造成 9 点伤害"
new DamageVar(4m, ValueProp.Move),
new DamageVar("Damage2", 9m, ValueProp.Move)

OnPlay:
    Damage(..., DynamicVars["Damage"].BaseValue, ...)   // 4，重复 2 次
    Damage(..., DynamicVars["Damage2"].BaseValue, ...)  // 9
OnUpgrade:
    DynamicVars["Damage"].UpgradeValueBy(2m);           // 只影响第一条
    DynamicVars["Damage2"].UpgradeValueBy(3m);          // 只影响第二条
```

**机制是原版验证过的，但要把"机制"和"玩法"分开说。** 原版"流光"（Glitterstream）在一张牌上
声明了两个同类型变量，升级时各改各的：

```csharp
new BlockVar(11m, ValueProp.Move),                   // 默认名 "Block"
new BlockVar("BlockNextTurn", 5m, ValueProp.Move)    // 显式命名
OnUpgrade: DynamicVars.Block.UpgradeValueBy(2m);
           DynamicVars["BlockNextTurn"].UpgradeValueBy(2m);
```

它的**玩法**是"获得 11 点格挡；下一回合再获得 5 点格挡"——第二个变量是下回合那个 **buff 的数值**
（存进 `BlockNextTurnPower`，在下一回合格挡被清掉时兑现），**不是**两条同时生效的格挡效果。
所以它证明的是**机制**（同类型变量可以起名各存一套、升级各改各的），不是"两条直接格挡效果"
这个玩法本身——后者原版没有对照。

直接的多次结算另有先例：原版"万象斩"（Omnislice）在一张牌的 `OnPlay` 里调了**两次**
`CreatureCmd.Damage`（第二次把同样的伤害镜像给相邻的敌人）。两条直接格挡虽无原版对照，
但机制与伤害同构（数量按值传入，格挡在生物身上累加），且生成的代码已对游戏程序集编译通过。
引擎对此也是预期之内的：`DynamicVarSet` 遇到重复键抛的异常里专门写了
"like 2 BlockVars for Halt, please specify a name for each one"——同类型多个变量要起名，
是引擎设计时就留好的路。

带名字的构造是游戏自带的（`DamageVar(name,…)`、`BlockVar(name,…)`、`SummonVar(name,…)`、
`MaxHpVar(name,…)`、`CardsVar(name,…)`、`PowerVar<T>(name,…)` 都有），所以同名撞车不存在。

**计算型的第二个数值**还需要一样东西：`CalculatedDamageVar` / `CalculatedBlockVar` 固定读
`CalculationBase` + `ExtraDamage`（格挡是 `CalculationExtra`）这几个名字，全游戏各只有一个。
所以**没占到原版名字**的槽由一个很小的运行时子类承载（生成时按需发出 `Runtime/SlotVar.cs`），
它覆写基类两个 `virtual` 方法去读**自己**那两个带序号的变量：

```csharp
// "先打 3×手牌数，再打 0.25×目标已损失生命"
new CalculationBaseVar(0m), new ExtraDamageVar(3m),
new CalculatedDamageVar(ValueProp.Move).WithMultiplier(DamageMultiplier),        // 第一条：原版形状

new DynamicVar("CalculationBase2", 0m),
new ModForge.Generated.Runtime.SlotExtraDamageVar("ExtraDamage2", 0.25m),
new ModForge.Generated.Runtime.SlotCalculatedVar(
        "CalculatedDamage2", "CalculationBase2", "ExtraDamage2", ValueProp.Move)
    .WithMultiplier(DamageMultiplier2),                                          // 第二条：读自己那两个
```

判据是"这个槽有没有占到原版名字"，**不是"同类里第几个"**：一张牌上"计算型伤害 + 计算型格挡"
时两者各自都是同类第一个，但基础值是按全局顺序编号的（伤害拿 `CalculationBase`、
格挡拿 `CalculationBase2`）——若按"同类第几个"发原版类型，格挡会静默读到**伤害**的基础值。
`newfx2` 里"淬火架势"（编译进 mod 的真实卡）与"混合计算探针"（生成文本）两处都钉着这件事。

子类的预览逐句照着原版写（附魔改写基础值 → 战斗中走修正钩子 / 战斗外手动套附魔 → 钳到 0），
所以附魔牌的卡面与结算都对得上。第一个槽始终走原版形状，单计算值的卡（绝大多数）生成的代码
与原版完全一致。

**基础值不再互相牵连**：每个计算型槽各占一个基础值变量（`CalculationBase` / `CalculationBase2`…），
升级各改各的。界面上那条"所有基础值的升级增长量必须相等"的旧提示已随之去掉。

**多段同值攻击**仍然推荐"一条效果 + 重复打出次数"（原版"千刀万剐"就是 1 点伤害重复 3 次）——
那是更简洁的写法。多个槽是为"各段数值不同"准备的。

#### 每效果一个槽：设计取舍

- **不合并同值**。两条都是"造成 5 点伤害"时不会共用一个变量，而是各占一个。合并看起来更省，
  但那样"升级其中一条"会连带改到另一条，与"每个效果独立"的目标冲突。
- **第二个及以后的计算型槽**由一个很小的运行时子类承载（`Runtime/SlotVar.cs`：只换"从哪个
  变量读数"），计算、卡面预览、升级重算、附魔预览都与原版逐句一致，没有行为差异。
- **「永久增伤」与「使某些牌伤害增加」会给目标牌的每一个伤害槽都加**（与"这张牌的伤害增加 N"
  的语义一致）。目标牌是运行时挑的，生成代码不知道它有几个槽，所以按命名约定扫描
  （`Runtime/DamageSlots.cs`：`Damage` / `Damage2` / …，只认**固定值**槽——计算型的基础值是
  算式的一部分，加它会把算式算出来的数再叠一层）。

#### 各效果独立后，这些原先的限制都不存在了

| 原先的行为 | 现在 |
|---|---|
| 两条伤害 → 变量取较大值，小的被顶上去 | 各占一个变量，各是各的 |
| 两条计算型伤害 → 第二条的算式被丢弃 | 各有各的算式与乘数方法 |
| 同一状态施加两次、数值不同 → 读同一个 `PowerVar` | 各占一个（`StrengthPower2`…） |
| 同一状态施加两次、时机不同 → 同上 | 各占一个，且两条都能收到钩子 |
| 升级 → 都改同一个变量 | 各改各的 |

`newfx2` 里有对应这些场景的卡与断言（"双重打击"两条固定值伤害、"双重清算"两条计算型伤害、
"逐步壮硕"同一状态不同时机、以及费用升级），改动回退时会立刻失败。

#### 施加状态：同样每效果一个槽

施加状态也走同一套槽位分配：**同一个状态施加多次时，各占一个 `PowerVar`**（`StrengthPower` /
`StrengthPower2`…），时机也可以各不相同。比如：

> 获得 2 点力量。回合开始时，获得 1 点力量。（打出时 + 回合开始时，同一个状态）

生成出来是**两个各算各的取值方法、两次 `PowerCmd.Apply`、两套各自的升级**：

```csharp
// 计算型的两条：各有各的字段
private decimal _calcBase0 = 2m;  private decimal _calcPerUnit0 = 2m;   // A
private decimal _calcBase1 = 4m;  private decimal _calcPerUnit1 = 4m;   // B
await PowerCmd.Apply<StrengthPower>(..., CalcAmount0(cardPlay.Target), ...);   // A：2×力量+2
await PowerCmd.Apply<StrengthPower>(..., CalcAmount1(cardPlay.Target), ...);   // B：4×敏捷+4
```

```csharp
// 固定值的两条、数值不同：各有一个 PowerVar，施加点各读各的
new PowerVar<StrengthPower>(2m),                    // 打出时读它
new PowerVar<StrengthPower>("StrengthPower2", 1m)   // 回合开始时读它
await PowerCmd.Apply<StrengthPower>(choiceContext, ... DynamicVars["StrengthPower"].BaseValue ...);
await PowerCmd.Apply<StrengthPower>(HookContext(),  ... DynamicVars["StrengthPower2"].BaseValue ...);
```

固定值这部分曾经是个真实的错：原先按状态类型名硬拼变量名，同一个状态施加两次就都读
`StrengthPower`——"回合开始时获得 1 点力量"被顶成了 2 点，升级也叠在同一个变量上。
现在每条效果各占一个槽，取值、升级、声明三处都按同一份规划走。

唯一要注意的是**卡面描述的占位符**：第一个沿用状态类型名（`{StrengthPower:diff()}`），
后面那些要写 `{StrengthPower2:diff()}` 才会被引用到（界面上会把它们都列出来）。
**自动描述只覆盖第一个**——卡面文字表达不了"同一状态加了两次"，原版也不这么做。

所以完整的清单是：**每一条带数值的效果各占一个槽，条数不限；种类之间也互不影响。**

| 项 | 一张牌能有几个 |
|---|---|
| 伤害效果 | 不限（各占 `Damage` / `Damage2`…；计算型则各占 `CalculatedDamage` / `CalculatedDamage2`…） |
| 格挡效果 | 不限（同上） |
| 施加某个状态的效果 | 不限（各占一个 `PowerVar`，时机可以不同） |
| 其它数值效果（抽牌、最大生命、伤害增益…） | 不限 |

伤害与格挡是**两套独立的变量**，所以"造成 2×手牌数+3 伤害"与"获得 4 点格挡"同卡共存当然没问题——
那个 `3` 进伤害的基础值、那个 `4` 进 `BlockVar`，升级也各改各的。原版"君主之刃"就是这个形状。

```csharp
// 同一张牌上：伤害走计算型、格挡走固定值，各是各的键
new CalculationBaseVar(3m), new ExtraDamageVar(2m), new CalculatedDamageVar(...)
new BlockVar(4m, ValueProp.Move)

OnUpgrade:
    DynamicVars["CalculationBase"].UpgradeValueBy(1m);   // 只影响伤害
    DynamicVars["Block"].UpgradeValueBy(2m);             // 只影响格挡
```

顺便说一句，游戏的 `DynamicVarSet` 对**重名**是直接抛异常的（它的错误信息里举的例子正是"2 BlockVars for Halt"，并叫人给变量另起名字）——所以"两个同名变量"这种事轮不到悄悄出错，它会当场炸。真正会静默出错的是**共用一个变量**（多条效果读同一个键），那才是前面几张表在管的事。

`newfx2` 里有"深渊凝视"（计算型状态 + 计算型伤害同卡）、"双重伟力"（同一状态同时机两次）、"逐步壮硕"（同一状态不同时机、数值不同）、以及一条"伤害与格挡共存"的断言，专门盯着这些结论。

计算型数值的「取自谁」在存档载入时也会规整：目标写成多个（所有敌人 / 随机一名敌人 / 所有友方 / 随机一名友方 / 所有人）时并没有"那一个目标"，会退回"取自自身"。界面本来不给这种组合，这一步是防手改过或旧版留下的 JSON。

例如（编辑器里就是这么填的）：

| 想要的写法 | 配置 |
|---|---|
| 获得 等于 自身力量 层数 的伟力 | 施加状态 · 计算型 · 来源 = 自身力量 · 每单位 1 |
| 恢复 等于 目标格挡 ×2 的 HP | 回复生命 · 计算型 · 来源 = 目标格挡 · 每单位 2 |
| 对 所有人 造成 等于 手牌数 的伤害 | 伤害 · 目标 = 所有敌人 · 计算型 · 来源 = 手牌数 |
| 消耗 等于 手牌数 ×0.5 张 手牌中的牌 | 消耗牌堆中的牌 · 计算型 · 来源 = 手牌数 · 每单位 0.5 |
| 造成 5 + 等于力量 的伤害 | 伤害 · 效果基础值 5 · 来源 = 自身力量 |

伤害与格挡的计算型会显示在卡面上（用的是游戏的 `CalculatedDamage` / `CalculatedBlock`，实时算出的值），其它种类在结算时计算。

**有来源时升级有两个部分**，因为数值由两段组成：

| 升级 | 改的是 | 例 |
|---|---|---|
| 升级时效果基础值 + | 固定那一段 | 5 + 力量 → 8 + 力量 |
| 升级时效果变量系数 + | 变量系数的增量 | 每组牌 +1 → 每组牌 +1.5 |

两者可以同时用。没选来源（固定值）的效果只有一个升级框。升级量都紧跟在它所升级的那一格后面。

**费用的升级**用卡牌级的那一格（「升级时费用变化」）：填 -1 就是"升级后少 1 费"，
生成 `EnergyCost.UpgradeBy(-1)`——原版最常见的升级方式（"痛击" -2、"全身撞击" -1）。
只有费用升级、效果都没升级时，`OnUpgrade` 也会照常生成。

#### 多次升级与等级表

上面那套是**增量模型**：每级加同样的量。要"每级加得不一样"（6 → 9 → 13），
或者"升级换算式来源"（0 级按手牌数、第 2 级改按弃牌堆张数），就用**等级表**：

把卡牌的「升级上限」设成 2 或更多，每条效果下面会出现「升级等级表」。每一级一行，
填这一级的数值；**留空表示沿用上一级**，所以只填真正变化的那几级就够了。
那几行是**绝对赋值**，不是增量：

```csharp
public override int MaxUpgradeLevel => 2;

protected override void OnUpgrade()
{
    switch (CurrentUpgradeLevel)
    {
        case 1:
            DynamicVars["CalculationBase"].BaseValue = 9m;    // 这一级就应该是 9
            DynamicVars["ExtraDamage"].BaseValue = 4m;
            break;
        case 2:
            DynamicVars["CalculationBase"].BaseValue = 13m;
            DynamicVars["ExtraDamage"].BaseValue = 1m;        // 第 2 级换了算式，系数也换
            break;
    }
}
```

换算式来源时，计算型的取值方法会**按等级分支**（第 2 级起读弃牌堆，否则读手牌）。
这是增量模型做不到的事——增量只改数字，改不了"从哪取数"。

三点如实说明：

- **卡名会显示 `+2`、`+3`**（游戏自己会根据 `MaxUpgradeLevel` 拼出来）。
- **卡面文字只有"升级前 / 升级后"两态**：游戏描述里能用的开关是 `{IfUpgraded:…|…}`，
  它分不出第几级。所以换算式来源时，描述要自己写，别指望它能逐级显示。
  原版 578 张里**一张多级升级的牌都没有**（`MaxUpgradeLevel` 只有诅咒牌用，且都设 0＝不可升级），
  这条路没有原版对照。
- **等级表与增量二选一**：填了等级表，生成器就按等级绝对赋值，不再叠加「升级时数值 +」。
  两边都填时校验器会提示"将以等级表为准"（静默地覆盖掉一半配置是最难查的那种）。

**费用升级**仍是增量语义（每级各减一次），等级表不影响它。

### 触发时机

每条效果可以指定何时生效，而不只是打出时：

- **打出时**（默认）、**打出后**
- **抽到时**、**被弃掉时**、**被消耗时**
- **回合开始时**、**回合结束时**
- **打出一张牌时**（看的是任意一张被打出的牌，见下一节）

所以「打出时造成伤害、回合结束时再造成一次」这类设计直接可以做，不必为它单独写一个新效果。

#### 打出一张牌时

前几种时机看的都是**此牌**，这一种看的是**任意一张被打出的牌**——原版"精密瞄准"（每打出一张技能牌就降价）、"踩踏"（每打出攻击牌降价）、"女妖之嚎"（每打出虚无牌降价）、"如此甚好"（每打出 3 张技能牌就回到手牌）都是它。

它有两个参数。

**哪些牌算数**，用卡牌筛选选：不限 / 按标签（打击、防御、小刀、奥斯提攻击）/ 按类型（攻击、技能、能力）/ 按关键词（消耗、虚无、固有、保留、奇巧、不能被打出、永恒）/ 按需要星辰 / 指定某一张牌。同一份筛选判定与"伤害增益""附魔范围"共用，三处不会分叉。

> 标签与关键词是两套东西：打击 / 防御是**标签**（`CardTag`），虚无 / 消耗是**关键词**（`CardKeyword`）。原版"女妖之嚎"按关键词判、"完美打击"按标签判，界面上分成两组，别混。

**是否启用计数器**。不启用时每打出一张符合条件的牌就触发一次（踩踏、女妖之嚎就是这么写的）；启用时每张符合条件的牌让计数器 +1，攒够「攒够几张触发」才执行效果并把计数器归零（"如此甚好"：每 3 张技能牌回手一次）。

计数器还要选「多久归零」：

- **本回合** —— 回合结束与回合开始**各归零一次**。两处都要：只靠回合开始，本回合末到下次回合开始之间读到的还是上一回合的累计值；只靠回合结束，回合外的时机又会看到过期数字。原版用战斗历史查询（`HappenedThisTurn`）天然没这个问题，我们用的是自己的计数器，就得自己把边界清干净。
- **本场战斗** —— 不用显式归零，战斗内的牌本来就是临时副本，战斗结束自然消失。

阈值填 1 等同于不启用（每张都触发），生成时不发计数器字段，描述也按"每当你打出一张…"写。

**能力牌不能用这个时机**：能力牌打出后归入 `PileType.None`（不进任何牌堆），而引擎只把钩子发给"待在战斗牌堆里"的模型——所以它连自己那一次出牌都看不见。校验器会拦下来并提示改成攻击 / 技能牌（它们打完进弃牌堆，会继续收钩子）。

写这一种时还有两处与**原版不完全逐字等价**，核对原版卡时要心里有数：

- 原版常配合 `AfterCardEnteredCombat` 做"这张牌是战斗中途中生成的，把之前打出的补算上"。我们的计数从这张牌进入战斗牌堆那一刻起算，所以**战斗中生成的**这类牌会比原版少算之前打出的张数（战斗开始时就在牌堆里的牌不受影响，那才是绝大多数情况）。
- 原版踩踏用的是 `BeforeCardPlayed`（在被那张牌结算**之前**），我们统一在 `AfterCardPlayed`（结算之后）。原版那样写只是为了抢在那张牌之前，对"降了多少费"的结果没有差别。

这个时机与「打出后」由游戏的**同一个**钩子派发（`AfterCardPlayed`），所以生成时会合成一个覆写：自身那半段包在 `if (cardPlay.Card == this)` 里，任意牌那半段各自按筛选判。各发一个的话是编译错误（同名 `override` 重复），只发一个则是静默少一种行为——两条路都试过，所以 newfx2 里有一张卡专门断言"只有一个覆写、两半都在"。

### 触发时机要求这张牌待在哪个牌堆

回合开始 / 回合结束这两类时机可以再限定牌堆：**任意 / 手牌 / 抽牌堆 / 弃牌堆 / 消耗堆**。选定后生成代码里会有一句牌堆检查，不满足就跳过，例如"回合开始时，若这张牌在抽牌堆中"就是 `AfterSideTurnStart` 里加 `if (Pile?.Type != PileType.Draw) return;`（逐条判断，所以同一时机下不同范围的效果互不影响）。

「回合结束时若在手牌中」不需要单独的效果或时机——它就是「回合结束时」+ 牌堆 = 手牌。载入旧工程时按这个规则读：先在 JSON 树上递归找到带 `trigger` 的效果节点改写再反序列化，因为 `System.Text.Json` 遇到枚举里没有的名字会直接抛异常，等对象建好再补救已经来不及。

同样在载入时规整的还有计算型数值的「取自谁」："取自目标"只对唯一目标有意义，目标写成多个（所有敌人 / 随机一名敌人 / 所有友方 / 随机一名友方 / 所有人）时并没有那一个目标，会退回"取自自身"。界面本来不给这种组合，这一步是防手改过或旧版留下的 JSON。

#### 牌堆范围看到的是哪一个"手牌 / 弃牌堆"

一个容易误会的地方：牌堆范围是**在那个钩子执行的时刻**去看牌堆，而不同钩子处在回合的不同位置。所以同一个"手牌"在回合开始和回合结束时看到的东西并不一样。

回合的先后顺序（来自游戏源码 `CombatManager`）：

| 顺序 | 阶段 | 这时手牌里有什么 |
|---|---|---|
| 1 | `AfterSideTurnStart`（回合开始） | 上一回合留下的牌（保留等），**本回合抽的还没进来** |
| 2 | 抽牌 | 手牌补满 |
| 3 | 自动打出相位（`AutoPrePlay`） | 手牌已满 |
| 4 | 自动打出相位（`AutoPostPlay`，回合结束） | 手牌未弃 |
| 5 | `OnTurnEndInHand`（回合结束时还在手上的牌） | 手牌未弃 |
| 6 | 弃手牌（手牌 → 弃牌堆） | 手牌清空 |
| 7 | `AfterSideTurnEnd`（回合结束） | 手牌已空 |

由此得出两条与实际一致的结论：

- **「回合开始时 + 若在手牌中」看到的是上回合留下的牌，不是本回合要抽的牌。** 这是引擎的真实时序，不是实现取巧：回合开始的钩子确实在抽牌之前。原版"乱战"（回合开始时打出抽牌堆顶）用的也是抽牌之后那个相位，正是为了解决同一件事。
- **「回合结束时 + 若在弃牌堆中」看到的是弃手牌之前就已经在弃牌堆里的牌**（含"回合开始时/结束时丢弃"这类效果丢进去的），不含本回合结束时手上那几张——那几张还要等弃手牌之后才进去。

「回合结束时 + 若在手牌中」这一条不靠牌堆判断实现，而是走游戏专门为此提供的钩子（`OnTurnEndInHand`，第 5 步）：它在弃手牌**之前**执行，正是"回合结束时还在手上"的语义。有个坑值得记下来——引擎调用它之前会把牌临时移进 `Play` 牌堆，所以在这个钩子里写"牌堆 == 手牌"反而永远不成立。原版的诅咒牌（凋萎、燃烧、疑虑…）用的就是这个钩子。

"持续到下一回合"这类跨回合的效果属于**状态**模块，不属于这张牌：状态的层数、衰减与回合触发由状态自己管理，卡牌的效果只在它自己的时机上生效一次。

### 重复打出次数

一条效果可以执行多次（「重复打出次数」）。除自动打出外，写法上它是整条效果的循环，
所以卡面文字接在句尾：

> 造成 4 点伤害，重复 3 次。

**升级时可以加次数**（填「升级时重复打出次数 +」）。这时次数会写成卡牌声明的 `Repeat`
变量，升级改的是那个变量——和游戏里多段攻击的做法一致。

#### 次数也可以是算出来的

把「重复打出次数来源」从「无」改成一个来源，次数就变成 `重复打出次数 + 每单位 × 来源`，
与数值部分是**各算各的**：

> 造成 5 点伤害。本场战斗中你每失去过一次生命，就额外造成一次伤害。

这是原版"扯碎"（TearAsunder）的形状。注意它的伤害是**固定 5**、次数才是算出来的——所以
次数有自己的一套「重复打出次数 / 重复打出次数来源 / 系数」，不共用数值那一套。两者若合成一套，
这张卡的伤害会跟着次数一起变成计算型（卡面显示的就成了"造成 等于失去生命次数 的伤害"）。
`newfx2` 里有一张卡专门盯这件事。

升级也分开：数值的升级改伤害（或格挡等），次数的升级改「重复打出次数」。

次数是算出来的时候，**升级有两格**：「升级时重复次数 +」（算式的**基础值**加多少）与
「升级时重复次数变量系数 +」（**系数**加多少，"每次多打一次"→"每次都多打两次"）。
两格都只在次数有来源时才显示——固定次数没有变量，也就没有系数可改。

#### 自动打出：重复的是"打出"，不是整条效果

「自动打出 → 某个牌堆」的重复**不重新选牌堆**：牌堆只查一次，循环里按
`打几张 × 重复几轮` 逐个打出（每打出一张它就离开牌堆，下一轮自然取到下一张）。
这符合直觉——"自动打出抽牌堆中的 2 张牌，重复 2 次"是打 4 张，
而不是"每轮重新挑一次牌堆再打 2 张"。

```csharp
var autoPlayPile = PileType.Draw.GetPile(Owner);   // 牌堆查询在循环外
for (int r = 0; r < 2; r++)                        // 重复 2 轮
    for (int n = 0; n < 2; n++)                    // 每轮打 2 张
        await CardCmd.AutoPlay(choiceContext, autoPlayPile.Cards[^1], null);
```

「自动打出 → 此牌」时**没有**「重复打出次数」这一组：那条路走引擎的自动打出手时机，
打几次由引擎决定，填了也没用（校验器会提示）。

### 提高 / 降低最大生命

### 提高 / 降低最大生命

**提高最大生命**对应 `CreatureCmd.GainMaxHp`，原版"狂宴"斩杀后永久加最大生命用的就是它。
这个改动**跨战斗保留**——它动的是玩家自己的最大生命值，不是战斗内的临时数值，所以与
"永久增伤"那种需要存档字段的效果不同，不需要额外支持。

数值从卡牌声明的 `MaxHp` 变量读回（原版声明的就是 `MaxHpVar`），所以卡面与升级都跟着走。

**降低最大生命**走 `CreatureCmd.LoseMaxHp`，两个接口在游戏里不同：
`GainMaxHp` 不接受 `PlayerChoiceContext`（只改上限再补回复），`LoseMaxHp` 接受
（当前生命高于新上限时，超出部分会作为不可格挡、不受增伤的伤害扣掉）。两个都只接受**非负数**，
负数会直接抛异常——要往另一个方向走请用另一个效果，校验器会拦下这种填法。

一张牌上同时"提高"与"降低"且数值不同时，卡面只能显示一个（游戏一张牌只有一个 `MaxHp` 变量），
显示的是提高的那个，校验器会提示这个冲突。

### 触发时机写在描述里

效果的触发时机不是「打出时」时，描述会自动带上时机，读起来才知道什么时候生效：

> **回合结束时，**对所有敌人造成 4 点伤害。
> **打出后，**抽 1 张牌。

时序是「回合结束时若这张牌在手牌中」这类较长的情况也照实写出来——牌堆范围会和时机拼成一句话。

> **回合开始时，若这张牌在抽牌堆中，**抽 1 张牌。

「打出一张牌时」这一句把筛选与计数一起说出来，中英语序各写各的（中文"打出一张技能牌"，英文"play a Skill card"）：

> **每当你打出一张技能牌，**获得 1 点格挡。
> **本回合你每打出 3 张虚无牌**，获得 1 点能量。

英文还要区分单复数，所以词表里 playedCard\*（单数）与 playedCards\*（复数）各一套，中文两套同字——`phrasetest` 会断言这几十个词都齐。

默认的「打出时」不写——那是绝大多数卡的情况，每条都写反而啰嗦。

### 星辰费用

卡牌页的「星辰消耗」一格，对应游戏的 `CanonicalStarCost`（原版 40 多张星费卡都是这么写的，
例如"星体脉冲"是 3）。**`-1` 表示不需要星辰**（默认），填 0 或更多就是打出时要花这么多星辰。

「升级时星辰变化」填的是升级时的**增量**（通常为负，`-1` = 升级后便宜 1 点），对应
`UpgradeStarCostBy(addend)`。

⚠️ **X 星的牌不能填「升级时星辰变化」**：游戏在 `UpgradeStarCostBy` 开头就
`if (HasStarCostX) throw`，而且只在升级时抛——卡面预览看不出来。校验器会拦下这个组合。
另外，只改星辰（不改能量）的卡也必须有 `OnUpgrade`，否则填了完全没反应——生成器已经算进去了。

> 如实说明：**「升级时星辰变化」没有原版对照**——原版星费卡升级改的都是伤害，`UpgradeStarCostBy`
> 在整个原版里没有任何一张卡调用过。接口本身是游戏提供的（文档写明"meant to be called in
> OnUpgrade"），形状正确性由 `cardtest` 对着游戏程序集编译来保证。

### 费用是 X

勾选「费用是 X」后卡面显示 `X`，打出时消耗全部能量，效果按消耗量结算。

⚠️ **X 费卡的效果里不能用「当前能量」取值**：游戏在效果运行**之前**就把能量扣掉了
（`CardModel.SpendResources`），那时读到的是 0。要取 X 的量，请用数值来源里的
「X 值（能量）」/「X 值（星辰）」，它们对应游戏的 `ResolveEnergyXValue` / `ResolveStarXValue`，
并且会把「化学 X」这类遗物的修正也算进去。

### 充能球（故障机器人）

| 效果 | 说明 |
|---|---|
| 生成充能球 | 可选闪电 / 冰霜 / 黑暗 / 等离子 / 玻璃，逐个生成（与原版一致：球位满了会自动激发**最右侧**的球） |
| 激发充能球 | 激发**最右侧**（或最左侧 / 全部 / 随机）的球 **m 次**，球在最后一次才被移出队列；可以只挑某几种球（多选） |
| 获得充能球栏位 | 增加球位 |

充能球名取自游戏自己的 `orbs` 表，所以卡面写的是「生成 2 个闪电充能球」。表里给的是**不带"球"字**的名字（"闪电""冰霜"），"充能球"由句式补上——两种语言的连接不同（中文直接连、英文要一个空格，见 `words.orbJoinSuffix`）；拿不到游戏目录时退回枚举名（`Lightning`…），不会出现"充能球充能球"那种重复。

这三条效果的数值**可以是算出来的**（"生成 等于 手牌数 个闪电充能球"），填了变量来源就走计算型的句式，不再把基础值当成结果写出来。

#### 激发：激发哪些球，以及"m 次"是什么意思

两格合起来决定激发哪些球：**哪一头**（四选一）× **哪些种类**（多选，留空 = 不限）。

**队列的首尾与画面的左右是反的**，这一格按画面说（原版文本与实现对得上号）：

| 选项 | 游戏接口 | 依据 |
|---|---|---|
| **最右侧**（默认） | `OrbCmd.EvokeNext`（队列的 `First()`） | DUALCAST 中文写"激发你最右侧的充能球两次"，实现是它 |
| **最左侧** | `OrbCmd.EvokeLast`（队列的 `Last()`） | CONSUMING_SHADOW 写"激发你最左侧的充能球" |
| **全部** | 数一遍球数、逐个激发 | SHATTER："激发你所有的充能球两次" |
| **随机** | 按 `Rng.CombatOrbGeneration` 挑一个 | 游戏没有这个接口，编辑器扩的（原版只有"队首 / 全部"） |

**种类**那一格是**多值输入**（`ui/components.js` 的组件）：逗号分隔、打字时有下拉提示、
失焦自动纠正格式（补空格、中文逗号与顿号都收成半角逗号、去重）。选中的种类按球在游戏里的
模型 id 判（`orb.Id.Entry == "LIGHTNING_ORB"`），所以将来游戏加球种也不会串。

数值 **m 是"每个被选中的球各激发几次"**，不是"激发几个球"：

- 最右 / 最左 / 随机 —— 只有那一个球，m 就是它被激发的次数；
- 全部 —— 每个球各 m 次（"碎片"就是 m=2）。

做法照抄原版：`EvokeNext(choiceContext, owner, dequeue: i == evokeCount - 1)`——前面几次
`dequeue: false` 让**同一个球**反复激发，最后一次才把它移出去。逐次都出队的话激发的是 m 个
**不同**的球，"激发最右侧的球两次"会变成激发最右和最左两个球——那是错的。

效果的**重复次数 n** 是另一层：把整件事做 n 遍（重复 2 次、m=1 就是"激发最右侧的球，
做两次"——两个球各一次）。所以"m 次 + 重复 n 次"各管一件事，不重叠。

**一个已知代价**：带种类筛选、或随机那一档，挑出来的球未必在队首，而游戏只给了"激发队首 /
队尾"两个接口（`OrbCmd.Evoke` 是私有的），所以生成代码会先把那个球挪到队首
（`OrbQueue.Remove` + `Insert(0, …)`，都是公开的普通列表操作）。激发的**是哪个球**因此与
作者写的一致，代价是队列顺序会被改（画面上球可能跳一下）。

### 召唤（亡灵契约师）

「召唤」的数值就是召唤物的生命值，写出来是「召唤 6」，与原版卡牌一致。底层走 `OstyCmd.Summon`。

⚠️ 游戏只有一个可召唤的对象（奥斯提，`OstyCmd` 直接写死了它），**没有**通用的「召唤任意生物」接口。要召唤自定义生物得自己写 `MonsterModel` 并配好贴图与场景，超出当前范围。

### 铸造（储君）

「铸造 N」对应 `ForgeCmd.Forge(N, 玩家, 来源)`，游戏自己处理整套逻辑：

1. 战斗里还没有「君王之剑」时，先生成一张加入手牌；
2. 把 N 加到**所有**君王之剑的伤害上（含消耗堆里的副本）。

写法与原版一致（卡面「铸造 5」用游戏的 `ForgeVar`，升级改它，`{Forge:diff()}` 可引用）。同一张牌可以有多条铸造，各占一个槽（`Forge` / `Forge2`）、升级各改各的；也支持计算型（「铸造 等于手牌数 的点数」）。

原版对照：铸剑者（纯铸造 30）、铸墙、大爆炸、征服者、追踪之刃、战利品、征召上前、战火铸就——这 8 张原先在审计里是「无法实现」，补上铸造后全部可直接实现。锻打成型仍做不到（它还要按"本回合击中该敌人几次"计算，缺这类历史计数）；淬炼刀刃是「实现方式不同」（另一半是下回合能量的 buff，缺 `AfterEnergyReset` 状态时机）。

### 附魔

给牌附魔，共用同一套选牌器（十步流程），另有一个**层数**：

| 字段 | 说明 |
|---|---|
| 挑哪些牌 | 流程一：这张牌自己 / 从牌堆里找 / 从卡组里找 / 按类型·牌 ID·标签·关键词·稀有度筛 |
| 从哪些牌堆找 | 流程二（选"从牌堆里找"或按某一维筛时）：可多选，空 = 全部战斗牌堆 |
| 怎么取 + 张数 | 流程九/十：全部 / 选择 N 张 / 随机 N 张 / 至多 N 张 |
| 附魔 | 附哪一种（锋利、腐化、动量……） |
| 附魔层数 | 每张附几层。和别的数值一样是**动态变量**，可以升级，也可以算出来（基础值 + 变量 × 系数） |

**"张数"与"层数"是两件事**，原版分得很清楚："墨刃"给 2 张小刀各附 1 层、"自学手册"选 1 张牌附 2 层。所以张数归选牌器（"附几张"），层数归效果数值（"每张附几层"）。附魔的数值是层数、不是张数，所以它的张数留在选牌器那一格（`<pickCount>`）；消耗牌相反——它的数值本身就是张数，所以张数写在自己的 `<base>` 里。

附魔种类取自原版（自定义附魔还需要图标等资源，所以这一步只支持原版），名字取自游戏自己的 `enchantments` 表。

选牌框里出现的牌 = 下面两类的并集：

```csharp
c => ModelDb.Enchantment<Sharp>().CanEnchant(c)                          // 能正常附魔的
  || (ModelDb.Enchantment<Sharp>().ShowAmount && c.Enchantment is Sharp) // 已有同种、且这个附魔有层数
```

**第一类交给游戏判**（`enchantment.CanEnchant`）："锋利"只能附攻击、"黏稠"只能附防御，诅咒牌与牌组里"不能被打出"的牌都不行。不自己写一套——自己判迟早与原版不一致。

**第二类是"加层数"的入口**：已经带同种附魔、且这个附魔**真有层数**的牌要留下，因为我们对它做的是加层数。两个条件都不能少：

- 不判"同种"——它们会被 `CanEnchant` 滤掉（已附魔的牌它一律不放行），就没得加了。
- 不判"有层数"——克隆 / 本能 / 腐化这类**计算时根本不看 `Amount`** 的附魔也会出现在选牌框里，玩家选中后什么都没发生。

"有层数"用游戏自己的 `ShowAmount` 判（原版用它声明"这个附魔的 `Amount` 有意义、要显示"）。22 个附魔里只有 8 个真的用 `Amount`：锋利、活力、动量、伶俐、迅速、灵巧、黏糊、播种。

**别改用 `IsStackable` 判**：`CanEnchant` 的最后一关是 `card.Enchantment != null && (!IsStackable || 类型不同)`，同种**且可叠加**的牌它本来就放行——拿它当例外等于什么都没加；而原版附魔**没有一个覆写 `IsStackable`**（全默认 `false`），那样写会让例外永不成立，"加层数"功能等于关掉。

**已经带同种附魔的牌直接加层数**，不走附魔接口。原因是那个接口第一步就检查 `CanEnchant`，而已附魔的牌在它那里一律不放行，于是它会抛异常——它内部那段"同种就 `Amount +=`"根本走不到。我们照那段的本意做。

这里**没有"放入位置"**：附魔不搬牌，位置无从谈起（早先它跟着牌堆那一格一起冒出来，是排版错误）。

### 重放（一张牌多打几次）

"重放"是**卡牌属性**，不是某条效果——它说的是"这张牌被打出时执行几遍"。游戏侧是 `CardModel.BaseReplayCount`，与费用、关键词并列。它有**两条独立的入口**，注意别混：

**① 卡牌自己的重放**（卡牌页的「重放次数」一格）

填 1 就是"这张牌打出两次"（原版"隐藏宝石"给别的牌 +2 也是改的同一个字段）。卡面上会出现游戏自己加的"重放 N 次"说明。

生成时发成一条 **[SavedProperty] 自有属性** `ReplayCount`（每张牌都有，默认 0 = 不重放），setter 把它写进 `BaseReplayCount`；标准值由 `AfterCreated()` 给（那个 setter 带 `AssertMutable()`，构造时是 canonical 实例、调不了）。

**为什么必须是自有属性、而不能只写在 `AfterCreated()` 里**：`BaseReplayCount` 是普通字段，**不进存档**（游戏只存 id + 升级等级 + 该类的 SavedProperty + 附魔）。而游戏源码里 `AfterCreated` 的说明明确写着 *"Extra logic that should be run after the card is created (**NOT during deserialization**)"*——读档走的是 `FromSerializable` → `AfterDeserialized()`。所以**只写在 `AfterCreated` 里的重放，读档后会归零**（这是一个真 bug，已修）。改成自有属性后，读档由存档回填，`AfterCreated` 只负责给新建的牌一个标准值——原版 `SpoilsMap` 就是这个形状。

标准值那一段带一个 `if (_replayCount == 0)` 守卫：读档不经过 `AfterCreated`，但战斗内的副本是**克隆**出来的（`CloneCard` 不调 `AfterCreated`），无脑覆盖会把副本上带回的值抹掉。

> 如实说明：原版 578 张里**没有任何一张牌天生带重放**——它只被"隐藏宝石""变形""士兵炖菜""剑圣之力"这类东西临时改，所以这条路没有原版对照可验证。

**② 给别的牌加重放**（效果页的「给牌添加重放」）

作用对象用统一选择器（某个牌堆 / 指定牌名 / 按条件 / 此牌），持续范围两档：

| 持续范围 | 生成 | 能否跨战斗 |
|---|---|---|
| 本场战斗 | `目标牌.BaseReplayCount += N` | 否（战斗中的牌是临时副本） |
| 永久 | `目标牌.ReplayCount += N`（① 的那条自有属性） | **保留**（原版牌走存档组件，见下） |

本 mod 的牌走 ① 的那条自有属性（天性值与永久加成记在同一处、一起进存档——以前永久加成另记一个 `PermanentReplay` 字段，两份要各自维护、容易对不上）；**原版牌**由运行时自动落到"存档组件"那条路（见下节），不再静默跳过。

**但实现上有一处与永久增伤不同**：重放最终写在普通字段上，升级/降级不会重建它，所以**不能**照抄那边的 `AfterDowngraded` 补差值——补了会在降级时多加一遍。

界面里这一格叫「额外打出次数」（不叫"效果基础值"，那词在这里看不出填的是什么）。

### 让伤害提高

只有**一条效果**（「使牌的伤害增加」），两个选择决定它做什么：

**挑哪些牌** —— 用那套统一的选牌器（见上节）。

| 想要的效果 | 流程一 |
|---|---|
| 使这张牌的伤害增加 | 这张牌自己 |
| 使所有打击牌伤害增加 | 按标签 → 打击牌（按**卡牌标签**判，与原版"精准"遗物同一做法，不是按名字） |
| 使某张具体牌伤害增加 | 按牌 ID |
| 使手牌里所有牌伤害增加 | 从牌堆里找 → 只勾手牌 |

**持续多久**

| 持续范围 | 做法 | 跨战斗保留 |
|---|---|---|
| 本场战斗 | 直接改那些牌的伤害值（原版爪击 Claw / 撕咬 Maul 的做法） | 不保留（战斗中的牌是临时副本） |
| 永久 | 写进目标牌自己类上的 `[SavedProperty]` 字段 | **保留** |

#### 永久增伤：目前只能作用于本 mod 的卡牌

**当前实现**走的是"改那张牌自己的数值"：生成的每张有伤害的牌都实现一个接口（`IPermanentDamageBoost`），把增益记在它的 `SavedProperty` 字段上——本 mod 的牌之间可以永久互相增伤。**作用于原版卡牌时，运行时自动落到"存档组件"那条路**（见下），不再静默跳过。

#### 存档组件：原版卡牌的永久强化（2026-09-25 新增）

原版卡的类改不了，但它的存档形状里有一个**本来就在**的 props 块（`SerializableCard.Props`）——游戏按属性名反射回填、找不到就跳过，联机同步也走它。运行时把组件**借道这个块**持久化：

- **数据**（`Runtime/CardComponents.cs`）：组件仓库按卡实例存（`ConditionalWeakTable`，不阻止 GC）；条目名 `MfDamageComponent` / `MfReplayComponent` 带 mod 前缀，**多 mod 各记各的账、互不覆盖**。
- **存档两头**（`Runtime/SaveComponentsPatch.cs`，Harmony postfix，游戏装 mod 时默认 PatchAll 自动打上）：写档时给有组件的卡的 props 塞条目（没组件的卡存档形状一个字节不变）；读档时读回仓库。
- **进战斗**（`ComponentHookHost`，经 `ModHelper.SubscribeForCombatStateHooks` 注册）：游戏进战斗时把每张牌组卡克隆进抽牌堆并让 `DeckVersion` 指回原件，然后才派发 `BeforeCombatStart`——host 在那里把组件应用到战斗副本（伤害槽 +N、重放 +N）。每场战斗各应用一次；战斗中效果再施加的 delta 由施加处立即体现。
- **边界**：组件效果在战斗内生效；牌组界面的悬停预览不显示 +N（那要拦 UI，另开一轮）。组件**不占附魔槽**、与附魔/升级互不干扰。

两个 `Apply` 辅助因此是三条路按牌的种类自动落位：本 mod 的牌走自有字段、其它 mod 的牌按方法名认（鸭子类型）、原版牌挂组件——生成代码一行没变。

生成出来的写法照原版「巨镰」The Scythe（游戏里唯一一张永久自增伤的牌）：增益记在 `[SavedProperty]` 字段上，数值由 `CanonicalVars` 从字段读出来（所以读档后还在），打出时改字段并按增量调整 `Damage`，同时把 `DeckVersion` 那张（牌组原件）也改一遍——战斗中的是临时副本，不改它出了战斗就丢了。

还有一处容易漏：**降级（`AfterDowngraded`）要从字段把增益补回去**。降级会从标准数值重建动态变量，把加过的值一起抹掉（原版巨镰的 `AfterDowngraded` 处理的就是这件事）。我们按累计增量补差值，比它按"基数 + 累计"重算更简单。

### 启用条件（每条效果一个"什么时候才生效"）

每条效果可以勾选「启用条件」：把**一个变量三件套与另一个变量三件套比较**
（左值 `{比较方式}` 右值），满足时这条效果才执行，不满足时它什么都不做——
但不影响同一张牌的其它效果。生成代码是整条效果外面的一层 `if`（含"重复 N 次"循环）。

- **两侧各自是完整的三件套**（基础值 + 变量来源 × 变量系数），与效果数值同一套读法：
  来源用同一张表（手牌数 / 星辰 / 状态层数 / 按条件数牌…），系数为 1 不写乘号。
- **六档比较方式**：不小于 / 不大于 / 大于 / 小于 / 等于 / 不等于。没有"是 X"——
  那是费用筛选特有的（X 费牌没有固定费用可比），条件比较的是两个数值。
- **可升级**：两侧的基础值与系数各有升级增量（"手牌数不小于 3"升级后变"不小于 4"）。
  条件不在等级表机器里（`EffectState` 只合成数值 / 次数 / 两个费用阈值），
  所以**多级升级对条件也是每级同样的增量**；条件值不占卡面占位符，
  卡面文字里的条件数字是**字面量**（升级后卡面那句话不跟着变——与"其它计算型的 +1"同一口径）。
- **出码**：条件不占变量槽——两侧的数存在生成类的私有字段（`_calcBase{n}`，与"就地计算"
  数值同一套机制，`CondSide0(target)` 取值），全固定的一侧直接写字面量、不设方法。
  升级语句是"字段 +="。多 mod 无关（条件是卡自己的代码）。
- **句子**：前缀由描述的中央拼装处统一插（时机之后、动作之前）——
  "回合开始时，若 手牌数 不小于 3，造成 6 点伤害。"。30 种效果各写一遍必然漏一半，
  所以只有一处实现（`ValueWording.ConditionPrefix`）。
- **UI**：勾选框「启用条件」在**效果名字的右边**（标题行里，与上移/移除按钮同排）；
  勾上后条件组（比较方式 + 两侧三件套）画在**效果选项之前**——效果 / 触发时机 / 目标
  那一行的上面：先说"什么时候才生效"，再说效果本身。
- **已知边界**：①"这张牌自己的自动打出"不走条件（它由引擎的相位钩子直接执行，
  校验器会提醒——触发时机的牌堆范围本身就是条件）；②两侧全固定时条件成立与否
  静态可知——恒不成立是 error（效果永不执行）、恒成立是 warn（条件是摆设），
  校验器直接说出来；③没有来源的那一侧填"系数升级"不生效，校验器会提醒。

### 效果（共享）

效果可以在「效果」页定义一次然后复用。因为效果会出现在多个地方（卡牌的效果列表、状态的回合触发），共享一份能让行为只有一个出处：改一次，所有用到它的卡牌与状态一起变。

引用按 **id** 关联，不按位置，所以调整卡牌内的效果顺序不会把引用指到别的效果上。编辑器会显示每个效果被引用多少次，校验也会报出失效的引用和没人用的效果。

### 状态（增益 / 减益）

生成的是真正的状态效果，会出现在状态栏、叠加层数、按回合衰减，并且能被任意卡牌（包括原版卡牌）施加。行为由四件事决定：如何改变伤害、如何衰减、每回合触发做什么、是否叠加。

常见形态：

- *固定增伤* —— 加算伤害，每回合末掉一层
- *持续伤害减益* —— 在持有者回合开始时造成伤害
- *光环* —— 不衰减，持续整场战斗

「施加状态 / 移除状态」里的状态列表同时列出本 mod 的状态与原版状态，名字按**界面语言**刷新。两类各按自己的语言显示，这条规则在整份界面里是一致的：

- **本 mod 的状态**用内容语言——它是你写的内容，和卡牌名一样，写成什么语言就显示什么语言；
- **原版状态**用界面语言——取游戏本地化表里的译名，切到英文是 `Strength`、`Vulnerable`，切到中文是「力量」「易伤」。

原版状态名读不到时退回模型 id 的整理形式，不会显示成空白或内部编号。这种情况有两个来源：游戏路径没配（读不到本地化表），以及**游戏自己就没给这个名字翻译**——257 个原版状态里有 19 个（`CRUSH_UNDER_POWER`、`DYING_STAR_POWER` 之类）在游戏数据里中英皆无，多半是内部或未启用的内容。原版卡牌则 576 张全都有译名。

状态触发里的数值只能是**固定值**（编辑器里也只提供固定值）。状态没有卡牌那套动态变量表，计算型数值没有可读的东西；写进工程文件的话校验器会拦下并说明原因。

触发的那条效果也有**作用对象**这一格（与卡牌效果同一套候选，见「作用对象」一节）。状态挂在生物身上、没有"打出时选定的目标"，所以老工程里那一档按旧口径落地（造物轴＝所有敌人、玩家轴＝自己），校验器会给一条提醒；想明确指定就选真正的档——以前这一格在状态页根本没有，只能靠那个隐含口径。

### 要填卡牌 / 状态 id 的地方可以直接输入

凡是让你指定一张牌或一个状态的地方（施加/移除状态、加入指定卡牌、附魔、伤害增益的筛选…），输入框都是**可输入的下拉**：从列表里挑，或者直接把 id 打进去。

原版有 570+ 张牌、250+ 个状态，在长列表里翻找很慢；而 id 是能查到的（参考页里就写着 `CARD.CLAW` 这种写法），直接打更快。列表里每一项都显示「名字 — id」，所以**按名字打和按 id 打都能筛出来**，打 `爪击`、`CLAW`、`CARD.CLAW` 都能找到同一张牌。选中后填进框里的是 id 本身。

输入框下面那行小字显示这个 id 现在指向什么，打错一个字母就会写「未知 id: …」，不必等到导出或进游戏才发现。

### 皮肤

在「皮肤」页选中一个已安装的皮肤包，编辑器会解析其中的骨骼文件并列出动画。各游戏时刻（待机、攻击、施法、受击、死亡、入场）可以绑定到其中某个动画。游戏按固定名字请求这些时刻，所以动画名不同的皮肤需要绑定才能生效；ModForge 会把这份重映射写进生成的 mod。

### 导出 mod

**导出 mod**（顶栏右上的按钮）会校验、编译并写出 mod 文件夹，默认落在 `build/`，
也可以把导出路径指到游戏的 `mods` 目录，那样产物就已经在正确位置（见下节）。启动游戏即可，
mod 默认就是启用的，不需要改设置。

生成过程会报告编译诊断，然后按游戏加载它的同样方式校验产物，能抓到那些否则只表现为崩溃或「卡牌不出现」的问题：

- 与游戏已有内容冲突的模型 id（会导致启动崩溃）
- 游戏无法实例化的类型（缺少无参构造函数）
- 卡牌被加进了牌池却引用了不存在的状态

## 界面：设置页与项目页

顶栏只有**每次编辑都要用**的三个动作：保存 / 另存为 / 导出 mod。语言选择、路径设置与
日志在设置页；新建、打开、在资源管理器中查看在项目页（起始页）。两页都是居中版心
（约 860px），表单比内容页更宽松——它们是一次看完整的东西，不需要铺满宽屏。

### 设置页

**语言**：界面语言管按钮与标签；内容语言管卡牌名字与描述填的是哪种游戏语言。
填内容时不必回这里切——名字与描述的输入框**右上角**就有同一个选择器。

**程序默认路径**：与"具体在做哪份项目"无关的那些出入口。

| 路径 | 是什么 |
|---|---|
| **游戏路径** | Slay the Spire 2 的安装目录。原版卡图、本地化文本、程序集都从这里读 |
| **导出路径** | 生成的可加载 mod 写到哪。默认 `build/`；指到游戏的 `mods` 目录就等于直接装好 |
| **卡面路径** | **素材库**：你自己攒图的地方。编辑器只读，从不删它 |
| **皮肤路径** | 除游戏 mod 目录与创意工坊之外，还去哪里找皮肤包；可留空 |
| **新建项目的父目录** | 新建/另存为时默认建在这里，子文件夹名取项目名 |

每个路径旁边有「浏览…」按钮，弹的是**系统原生**的文件夹选择框（资源管理器同款）。浏览器的
`<input type="file">` 出于安全只能给出文件内容、给不出真实路径，而"打开项目"需要的恰恰是
一个目录路径，所以这一步只能在编辑器进程里做。对话框开着时其余请求照常响应（弹窗跑在
后台线程上，不占请求循环）。

这些路径存在程序旁边的 `settings.json` 里，**不进项目文件**：它们描述"这台机器上东西在哪"，
而项目描述"要做成什么"。分开之后项目可以原样发给别人，各人自己配路径。
命令行也能临时覆盖：`ModForge.exe --game <路径> --project <项目文件夹>`。

**自动生成描述的句式**：描述句子不在代码里，而是按语言放在 `language/sentences/` 里，一种语言一个
文件。加语言只要复制一份改内容，不必重新编译——所以把它的位置与已有语言列在这里，否则没人
知道该往哪放文件。

**输出**：校验结果与生成过程的日志。诊断用，所以也在设置页。

### 项目页（起始页）

三个入口：**新建项目**、**打开项目**、**在文件资源管理器中查看**。下面是当前项目的位置、
mod 封面与元信息。

页面上只列两条路径（项目文件夹与封面）——里面的目录布局是固定的，逐条列出来只是占地方。

项目是一份**独立文件夹**，以项目名命名，内部布局**固定且不可自定义**（八个文件夹，见上面
「工程文件夹长什么样」一节）。

这八处的名字与位置写死，是为了让"打开"任何一份项目都知道该去哪里找东西，项目文件夹也可以
原样拷给别人。所以界面上只把它们显示出来，不给编辑框。

**封面是可选的**：选一张图，保存时收进 `About/Preview.png`（别的格式会先转成 PNG——
没装 Godot 就按原样放进去）；再选一张新的，旧的会被替换。不选也行，那份文件就不存在。

**保存只带用到的素材。** 编辑时卡图可以引用素材库里的任何图（素材库是你自己攒图的地方，
想放多少放多少）；保存时只把真正被引用的那些复制进 `Cards/`，并顺手删掉项目里**不再被任何
卡牌引用**的文件（换过立绘留下的孤儿）。素材库本身**不会被清理**——那是你的图，编辑器不碰。

**同名时会先问一句。** 新建与另存为时若目标文件夹已存在，会弹确认框说明"哪个名字、在哪个
路径"，由你决定是否覆盖；不确认就不动。这样既不用一直挂着一个"覆盖"勾选（开着危险、关着
还得回来改），也不会悄悄动别人的项目。

### 保存的是项目，导出的是 mod

| 操作 | 产物 | 能不能再打开 |
|---|---|---|
| **保存 / 另存为** | 工程文件夹（下面那八个） | 能，「打开项目」选文件夹读回来 |
| **导出 mod** | `<工程>/Mod/<ModId>/` 下的 `.dll` + `.json` + `.pck` | 不能，那是给游戏加载的产物 |

导出前会先保存一次，所以改了没点保存也不会导出旧版本。

## 工程文件夹长什么样（文件模块）

一份工程就是一个以工程名命名的文件夹，**自足、可拷贝、可分享**：

```
<工程名>/
  About/          工程信息
    About.xml       mod 元数据（名字 / 作者 / id / 版本 / 简介…）
    Preview.png     可选，mod 封面（**文件名写死**就是这个）
  Language/       本地化，一种语言一个文件夹
    eng/
      Localization.xml   翻译键：<LanguageData><cards><MY_CARD.title>…
    zhs/
      Localization.xml
  Textures/       卡框、效果、遗物等贴图（目前是状态图标）
  Skins/          皮肤：源皮肤包（.pck）收在这里
  Cards/          卡面
  Source/         生成的 C# 源码，供查看与对照
  Mod/            导出的可加载 mod（.pck / .dll / .json）
  Create/         定义，一个实体一个文件
    Cards/<卡 id>.xml
    Effects/<共享效果 id>.xml
    Powers/<状态 id>.xml
    Skins/<角色>.xml
```

几条约定：

- **定义与文本分家**。`Create/` 放结构与数值，`Language/` 放玩家看得到的话——与 RimWorld
  一样，改一句翻译不必去碰定义。卡牌的名字与描述**只在语言文件里**，卡文件里没有。
- **`About.xml` 参考 RimWorld 的写法**：`<name>` / `<author>` / `<packageId>` / `<description>` /
  `<modVersion>` / `<supportedVersions>`。其余三项是编辑器自己的：`<affectsGameplay>`、
  `<typePrefix>`、`<selfCheckOnStartup>`，外加 `<preview>`（记的是封面文件名，值就是
  `Preview.png`——它是个记录，不是配置项）。
- **翻译键就是游戏用的键**：元素名是 `<条目>.title` / `<条目>.description`，条目名由生成的类型名
  算出来（`Kx` + `AlphaCard` → `KX_ALPHA_CARD`）。所以语言文件里的每一行都能直接对上游戏里的键。
- **一实体一文件**。删掉一个实体的文件就等于删掉这个实体；反过来，在编辑器里删掉实体再保存，
  文件也会跟着删掉（否则下次打开又"复活"）。
- **与默认值相同的项不写**。卡文件里没写的字段就是模型的默认值，所以把某一行删掉就等于恢复默认。
  例外是"这张牌是什么"那一组（牌池 / 类型 / 稀有度 / 目标 / 费用 / 升级次数 / 重放），它们总是写出来，
  好让一个卡文件一眼看得出这是张什么牌。
- **素材只在保存时收进工程**。编辑期间卡面可以指向你的图库（设置里的"卡面路径"），保存时才把
  用到的那些复制进 `Cards/`，引用改成文件名；不再被引用的会在同一次保存里清掉。图库本身从不被删。

**打开工程文件夹时不信任里面的 XML**：解析前拒绝 DOCTYPE 与实体声明、不给外部实体解析器，
所以从别人那里拿来的工程不会因为一段 XML 去读你机器上的文件。单个字段写错、某条效果读不动，
都不会让工程打不开——见下节「读到写坏的文件怎么办」。

### 一条效果怎么写

数值与次数**各有一套三件套**（`数值 = 基础值 + 变量 × 变量系数`），所以效果里是两块对称的结构。
两块的组成部分同名——路径不同，含义由所在的那一块决定（`base/count` 是数值的基础值，
`repeat/count` 是次数的基础值）：

```xml
<li>
  <kind>DealDamage</kind>          <!-- 这条效果是哪种（写错会报错并列出合法值）-->
  <target>AnyEnemy</target>
  <base>                           <!-- 数值三件套 -->
    <count>6</count>               <!-- 基础值 -->
    <source>HandCount</source>     <!-- 变量（来源）。没写 = 固定值 -->
    <coefficient>2</coefficient>   <!-- 变量系数 -->
  </base>
  <repeat>                         <!-- 次数三件套，同样是那三件 -->
    <count>1</count>
    <source>HpLostThisCombat</source>
    <coefficient>0.5</coefficient>
  </repeat>
  <pick>                           <!-- 挑哪些牌：选牌器十步流程（只有会挑牌的效果才有这块）-->
    <source>Piles</source>         <!-- 流程一：此牌 / 牌堆 / 卡组 -->
    <mode>AtMost</mode>            <!-- 流程九：全部 / 选择 / 随机 / 至多 -->
    <piles><li>Hand</li></piles>   <!-- 流程二：在哪些牌堆里找（可多选；空 = 全部战斗牌堆）-->
    <dimension>CardType</dimension><!-- 流程一/三：按哪一维筛 -->
    <types><li>Attack</li></types> <!-- 流程四（稀有度 / 牌 ID / 标签 / 关键词同理，各占一格）-->
    <pickCount>                    <!-- 流程十：张数（三件套）——**只在"张数不是效果数值"时写** -->
      <count>2</count>
      <source>HandCount</source>   <!-- 没写 = 固定张数 -->
      <coefficient>0.5</coefficient>
    </pickCount>
  </pick>
  <upgrade>
    <li><level>2</level><base><count>9</count></base></li>   <!-- 等级表：这一级就是 9 -->
    <li><base><count>3</count><source>DiscardPileCount</source></base></li>
  </upgrade>
  …这条效果自己的其它参数（targetPile / placement / cardId / costDuration / orb…）
</li>
```

消耗牌那种"**张数就是效果数值**"的效果不写 `<pickCount>`：它的张数写在自己的 `<base>` 里
（`<base><count>2</count></base>` = 消耗 2 张，"升级时张数 +1"也走 `<upgrade>`）。
文件里给它写了 `<pickCount>` 会**报一条错误并忽略**（那看着像生效了，其实什么也没做）。

- **`<pick>` 整块是默认时整个不写**（默认 = 从全部战斗牌堆里挑 1 张、不筛）；
  写了的话 `<source>` 与 `<mode>` 一定在（一眼看出这条效果挑的什么），其余按"与默认不同才写"：
  空的取值列表不写，`<pickCount>` 只在流程九不是"全部"（张数用得上）、且张数真与默认（1 张、没有变量）
  不同、且这条效果的张数不由效果数值给时才写。
- **"一个牌堆都不勾"与"没写 `<piles>`"是同一件事**（= 全部战斗牌堆，含出牌堆）。
  想表达"整手牌"就要显式写 `<piles><li>Hand</li></piles>`。
- 哪条效果能写哪几个 `<source>` / `<dimension>` 由它自己的策略决定（见「一套选择器：十步流程」），
  写了这条效果不支持的组合，校验器会报出来。

- **三件套里与默认相同的项不写**：固定值只有 `<count>6</count>`，系数是 1 就不写系数。
  整块都是默认时那块整个不出现，所以一条效果通常两三行，删掉哪一行就等于把那一项恢复默认。
- **`<source>` 的额外参数**（`<actor>` 取自谁、`<power>` 哪个状态、`<scope>` 从哪个范围数、
  `<filter>` 数哪些牌——那是一个**多维筛选块**，与选牌器那六个维度同一形状）
  与它平级，只有非默认时才写。
- **升级有两条路，靠有没有 `<level>` 分开**：
  - **有 `<level>`**：**等级表**，写的是**绝对取值**；同一块里没写的项**沿用上一级**
    （只想改系数就只写 `<coefficient>`）。每一级把该级该有的数直接写上去，
    所以它表达得了"每级加得不一样"，也表达得了"升级后改用另一个变量算"。
  - **没有 `<level>`**：**增量**，写的是"每级加多少"（`效果 = 等级 × 增量 + 初始值`），
    只能有一份；块里的 `<source>` 是**升级后换用的变量**（只换变量、不加数，也可用）。
  - **两者同在时等级表优先**：填了等级表的那条效果，它的增量不再叠加。
    同一条卡上没填等级表的效果不受影响——它的增量照旧每级加一次。
- **同一个元素名在两种地方含义不同**：三件套写在效果自己身上是"缺项即默认"，
  写在等级表里是"缺项即沿用上一级"。这是等级表能表达"只改系数"的前提。
- **`NULL` 是空，`None` 是无**——两者不是一个概念：
  - `NULL` 是"没有值"的通用兜底：**任何读不动的值都当它**。顶层写 `<source>NULL</source>`
    等于没写（固定值）；等级表里写它是"这一项沿用上一级"。
  - `None` 是变量来源枚举里的"无"，明确表示"这个数值没有变量"。等级表里
    `<source>None</source>` 是**"这一级不要变量了"**（换成固定值），与 NULL 完全不同。

`About/About.xml` 里空的项不写（没有作者就不写 `<author>`）；封面**固定**是
`About/Preview.png`——选了别的格式会被转成真正的 PNG（没装 Godot 就按原样放进去），
文件不在就是没有封面（不会因此让别的地方出错）。

### 读到写坏的文件怎么办

**工程照常打开，问题逐条报出来。** 读取这一侧全部按"不可信输入"来写：

| 情况 | 处理 |
|---|---|
| 认不出的元素名（多半是拼错） | 忽略它，记一条（写明位置，例如 `effects/li[2]/base`） |
| 枚举值 / 数字写错 | 那一项退回默认值，记一条并列出合法值 |
| 一条效果读不动（缺 `<kind>`） | 只丢**这一条**，这张卡的其它效果照读 |
| 一个文件整个读不出来（XML 语法错、缺 id） | 只丢**这一个实体**，其它文件照读 |
| About.xml 读不出来 | 用一份默认的继续，id 取工程文件夹名 |

每一处都带**文件与文件内的位置**，打开工程时在界面里弹出来、并写进日志。
不能因为一处写错就让整份工程打不开（那等于丢掉了整个工程），也不能一声不吭地降级
（那会让"我明明写了却没生效"变成一场猜谜）——这条折中就是"读取组件"的职责。

唯一的例外是 XML 语法本身坏掉、或带 DOCTYPE/实体声明的文件：前者没有内容可读，
后者**必须拒绝**（拒绝的是 DTD 本身，不是看它想干什么——那是不信任输入的第一条）。

## 生成的 mod 是怎么工作的

导出后，工程自己的 `Mod/` 下就是可以直接放进游戏 `mods` 目录的文件夹：

```
<工程>/Mod/<ModId>/
  <ModId>.json     清单（id 必须与文件名一致）
  <ModId>.dll      编译后的内容：每张卡一个 CardModel，每个状态一个 PowerModel
  <ModId>.pck      本地化文本、效果数据、立绘、皮肤资源、动画绑定
```

设置页那个"导出后另外复制到哪"留空时，产物就只在工程的 `Mod/` 里。把它填成游戏的 `mods`
目录（例如 `...\steamapps\common\Slay the Spire 2\mods`）就变成"导出即安装"，省掉每次手动拷贝。

卡牌通过 `ModHelper.AddModelToPool<IroncladCardPool, T>()` 注册；没有牌池的卡牌会在预加载阶段抛异常，所以注册是必须的而不是可选的。状态则完全不需要注册——游戏会自动发现每个 `PowerModel` 子类，这正是状态能做到「真状态」的原因。

代码用 Roslyn 在进程内编译，直接引用游戏自带的程序集，所以构建时不需要联网，也不需要额外 SDK。

**卡牌核心模块**（`Modules/Cards/`）把"这张牌本身是什么"收成一处：ID、能量费用、星辰费用、
升级费用变化、升级星辰变化、X 费、X 星、关键词、类型、稀有度、重放。以前这些散在四处各判
一遍（模型、生成器的九个位置、校验器、界面表单），改一处就会漏掉几处，而漏掉的表现往往是
**"填了没反应"**——最难发现的那种。

`CardCore` 是 `CardDef` 的**视图**，不是新的存档形状：工程 JSON 不变，既有工程照旧能用。
视图的价值是把"默认值归一"（例如星辰费用 `-1` = 没有）、"哪些属性真的会被生成"、
以及校验读的那份状态都集中表达；生成与校验读同一份，不会脱节。

**效果模块**（`Modules/Effects/`）分成两层：共用层（见上）与 `Kinds/` 里的
**一个效果一个文件**。已搬进 `Kinds/` 的，它的三个面（出码 / 句子 / 界面元数据）都在自己
那个文件里；`EffectCatalog` 是唯一的查表处，替代原来散在生成器、描述、界面里的三处 `switch`。

**描述模块**（`Modules/Descriptions/`）管"怎么说成人话"：句式表、共用词、选牌与数值的说法、
名词、占位符。**一条效果自己的句子不在这里**——它跟这条效果的出码同文件（`Kinds/`），
因为"这条效果好念成什么"取决于它有哪些参数，两件事分开写就一定会脱节；
描述模块提供的是"怎么说"，效果文件决定"说哪句"。两个模块之间只有一根反向的线：
描述模块要问效果目录"这条效果由谁来说"（`EffectCatalog.Find`，见 `PendingSentences`）。

**共用辅助不重复**：目标循环、数值表达式、选牌出码留在 `EffectEmitter`，
句式用词在描述模块——实测它们被引用得很密（`PickCardsLines` 12 处、`PickLabel` 11 处、
`EmitAgainstTargets` 9 处、`PileSuffix` 9 处），所以每个效果文件都很薄，只写差异。

**`EffectDef.cs` 没有搬**：它是效果的**词汇表**（效果模型与全部枚举），卡牌模型、选牌模块、
校验器、界面都在说这套词汇，搬进效果模块会让选牌模块反过来依赖效果模块。

**六批全部完成（30/30），三处旧 switch 已随之消失**：`EffectEmitter.EmitOnce` 的 case 只剩
AutoPlay 自档的空 break、`PendingSentences` 只剩入口分发与 `unknown` 兜底、
`EditorSchema` 里 30 种全部走 `EffectCatalog.SchemaOf`。`kindtest` 断言目录覆盖整个枚举、
界面 effects 列表无重复（同一种类出现两次——旧条目漏删、新条目又补了一条——实测踩过一次）。

批 2 是"共用形状的家族"（`EmitAgainstTargets` + `AmountExpr`），批 6 是选牌类（最难，放最后）。
`EffectKind` 的枚举顺序不改（它按名字序列化）。

**批 2 的做法**和批 1 一样：目标循环（自己 / 目标 / 全体敌人 / 随机敌人 / 全体友方）
留在共用层，六个行为只写"对每个目标做什么"——所以每个行为就是一个
`a.AgainstTargets(target => …)` 加上自己那句命令与属性。
它们各自**选自己的句式**：伤害与格挡按"给自己还是给别人"分两条（`damage` / `damageOther`），
回复生命也一样，而失去生命与两个最大生命只有一种说法（给别人扣血用"造成伤害"更准确）。

**搬迁时夹具要跟着长。** 这六条的"选哪条句式 / 发哪条语句"从共用层挪进各自行为之后，
**没走到的分支就等于没验**——批 2 时上面每一条只覆盖了一种形状（例如格挡只试过"给自己"、
回复与两个最大生命只有固定值），所以补了十张夹具把两条轴都铺开：
目标轴（给别人 / 给队友）与数值轴（计算型）。这条教训在批 1 上记过：
夹具没覆盖时逐字节 diff 为空说明不了任何事。

**批 3 的四种各成一类**（不共用形状）：抽牌是牌堆命令、铸造整套逻辑在 `ForgeCmd.Forge` 里、
召唤要**先播施法动画再召唤**（两句一起发）、立即执行灾厄判定把判定交给 `DoomPower`
（规则挂在灾厄状态自己身上，复刻一份就会静默不跟）。只有灾厄判定走目标循环
（它作用于别人），另外三条固定作用于自己。批 3 同样按"两条轴"补了夹具：
`Summon` / `Forge` 的计算型、`TriggerDoom` 的另两种目标写法（全体 / 随机）。

批 3 还顺手收掉两处：**召唤的"算出来的"句子**（补 `summonCalc`，见上）、以及
`PendingSentences.TemplateKey` **整张表已经空了**（搬到批 3 时，所有会走到它的种类都已在
`Kinds/` 里）——所以删掉它，兜底直接写 `Render("unknown")`：phrasetest 会断言没有任何形状
走到那一支，"新增种类却忘了写描述"仍然当场现形。

**批 4 是"施加 / 移除状态"两条**，都走目标循环；`ApplyPower` 与旧写法一字不差
（`PowerCmd.Apply<T>(ctx, 目标, 数值, 施加者, 来源牌)`）。移除状态这一批长了三件东西：

- **移除方式**（`PowerRemoval`）：`All` 整个移除 / `Partial` 只减层数。减层发的是
  `PowerCmd.ModifyAmount(ctx, 状态, -数值, 施加者, 来源牌)`——**负数即减少**，降到 0 由游戏自己的
  `ShouldRemoveDueToAmount()` 收掉，不自己写"先减再判 0 再移除"。数值字面量本身可能是负数，
  所以拼成 `-(值)` 包一层括号（`-(-1)` 才是"加一层"）。
- **移除对象**（`PowerSelection`）：按状态 ID / 所有正面 / 所有负面。后两种遍历
  `目标.Powers.ToList()`，用游戏自己的 `TypeForCurrentAmount` 分正负——**不自己按数值符号判**：
  那个属性就是卡面数值颜色用的同一判据，层数为负时的极性翻转由它负责。
- **数值三件套 + 升级**：`Partial` 才给数值格与升级格；`All` 时界面把数值格置灰，校验器也会
  警告"整个移除时写了数值（不会生效）"。`ApplyPower` 一直都有。

出码形状因此分两种：按 ID 的"只减层数"要先 `GetPower<T>()` 判 null 再改，是多行语句，
共用层为此多了一个 `AgainstTargetsBlock`（多行版；单行的 `AgainstTargets` 与旧输出逐字节相同）。
`using MegaCrit.Sts2.Core.Entities.Powers;` 只在**用到**遍历（所有正面 / 所有负面）那条路的卡片
文件里加——**条件 using**，否则其余卡片的产物会跟着变，逐字节对比就失去意义。
夹具 `POWER_REMOVAL_PROBE` 把四条出码路径都走一遍（按 ID·整个 / 按 ID·只减 / 正负·整个 / 正负·只减），
由 `picktest` 的编译网兜住。句子新增 6 条模板，`{name}` 只在按 ID 时替换。

**批 5：加入指定卡牌长了"两种生成方式"**（`AddCardMode`，用户定的设计）：

- **指定牌**（`Named`）：加 `<cardId>` 那一张（可升级版），原版"愤怒"的写法。
- **从卡池 N 选一**（`ChooseFromPool`）：从**出牌者自己的角色卡池**
  （`owner.Character.CardPool.GetUnlockedCards`）按多维筛选筛出候选——筛选与选牌器
  **同一个谓词生成处**（`CardPickFilter`），但没有"牌堆 / 卡组"那些运行时范围维度，
  费用阈值用筛选自带的常数（卡池里都是卡面印着的费用）。随机取 N 张：
  N=1 直接加入（可加多张、可重复，原版"变身"同款 `GetForCombat`）；
  N≥2 每张弹游戏自己的选牌界面（原版"发现"的 `FromChooseACardScreen`，
  三选一那类），选中的加入目标牌堆。
- **硬约束**：游戏那条选牌界面候选超过 3 张直接抛异常——校验器把候选数拦在 1~3；
  候选 ≥2 时效果数值不参与（每轮固定加入一张选中的牌），校验器会提醒。
- **两种生成方式都是临时牌集合的"写侧"**（生成的牌存进集合，供同牌后面的效果再动），
  但它不是"读侧"——它不挑牌、不改造牌。XML 是 `<addMode>` / `<candidates>` / `<poolFilter>`。
- 原版对"战斗中生成"自有一道门槛（工厂内部的 `FilterForCombat`：排除基础 / 远古 / 事件
  稀有度与声明了不可生成的牌），走工厂方法自动生效。
- 这一批顺带修掉一个旧句子的毛病：`addNamedCard` 的 {where} 念的曾是**选牌来源**
  （"加入所有牌堆"），现在两条路都念**目的地**（"加入手牌"）。

批 6 与批 7（升级 / 变化 / 搬运 / 复制 / 降费 / 免费 / 附魔 / 增伤 / 重放）是选牌类收尾，
出码与描述照旧形状搬进各自文件，没有行为变化（产物逐字节一致）。工程细节记两条：
自动打出的"牌堆档"在共用层 `Emit` 有直通道（它的"重复"作用在**打出**上、不重新取牌堆，
见 `AutoPlayBehavior`）；增伤与重放的局部变量序号用**独立计数器**（`NextBoostIndex`），
与选牌变量的编号序列分开——共用的话多写一条增伤会把一堆无关生成代码的编号整体平移。

### 伤害与格挡**不合并**（查证过）

它们看起来可以合并，因为原版把两者的计算基础值挤在同一个变量里：
`CalculatedVar.GetBaseVar()`（`CalculatedVar.cs:94`）对伤害与格挡**都返回 `CalculationBase`**，
两者只差增量变量（`ExtraDamage` / `CalculationExtra`）。

但那是**原版的限制**，而我们的生成器已经故意把它们各给一个（`CalculationBase` / `CalculationBase2`），
为的是避免"改一个另一个跟着变"。所以合并**省不到任何槽**；而游戏里伤害与格挡是两条不同命令
（`CreatureCmd.Damage` / `GainBlock`）、不同 `ValueProp`、卡面与升级处理也不同。结论：保持独立。

它们真正重复的是**形状**（"把一个数值作用于目标"），那由共用辅助承担，不需要合并概念。

### 时机模块（`Modules/Timing/`）：什么时候触发 → 发哪个游戏钩子

时机是**第七个横切关注点**：同一个效果可以挂在任何时机上（打出时 / 抽到 / 弃掉 / 消耗 /
回合开始结束 / 打出一张牌时），所以它不属于任何单个效果。它牵动的分支很碎，而且**每一条
错了都不会报错，只是不触发**，所以值得单独成模块：

- **两条触发轴落到同一批钩子**：卡牌效果的 `EffectTrigger`（8 个）与状态的 `PowerTrigger`
  （4 个）最终都落到同一批游戏钩子上（如 `EffectTrigger.StartOfTurn` 与 `PowerTrigger.TurnStart`
  都落到 `AfterSideTurnStart`）。`HookSpec` 是**唯一**那张"时机 → 钩子"表。
- **"打出后"与"打出一张牌时"落到同一个钩子**（`AfterCardPlayed`），必须合成一个覆写——
  各发一个的话后者会覆盖前者（同名 override 重复定义是编译错误）。而且两者同在时不能早退，
  得把"自身"那半段包进 `if` 里。
- **"回合结束时 + 若在手牌中"是另一个钩子**（`OnTurnEndInHand`）。用 `AfterSideTurnEnd`
  的话永远不成立——引擎在弃完手牌之后才发那个钩子。
- **"自动打出这张牌"走自动打出的相位钩子**，不能混进普通回合钩子（会变成打出时又打出自己）。
- **`ShouldReceiveCombatHooks` 要按全部依赖钩子派发的效果算出来**，漏算的后果是静默的：
  代码编译正常、牌也在牌堆里，只是那个钩子永远不派发过来。注意"在手牌里"那条**不算**——
  它由引擎逐张手牌直接调用，不走派发。

两处**写错就编译不过**的细节，由那张表统一持有（以前在卡牌侧与状态侧各写一遍）：

| 细节 | 事实 |
|---|---|
| 访问修饰符 | `OnPlay` 与 `OnTurnEndInHand` 是 `protected virtual`，`After*` 那一族是 `public virtual`——游戏自己就不统一，写错是 CS0507 |
| 签名格式 | 卡牌侧一律**单行**参数；状态侧长签名**多行**，且右括号跟在最后一个参数行尾。两边不一致，是现状，搬迁时逐字节保留 |

> 访问修饰符这一条是逐字节对比抓出来的：我一开始统一写成 `public`。快照只比文本、不编译，
> 所以这类错误要同时靠编译类工具（`newfx2` / `modprobe`）兜住——两道网各管一半。

### 计数模块（`Modules/Counting/`）：所有"数出来的"来源

**收录 30 种**，按来源分四类：

| 来源 | 数量 | 是什么 | 需要共享吗 |
|---|---|---|---|
| 游戏战斗历史 | 20 | 打出/抽到的牌数、失去生命次数、受击次数、攻击次数、消耗/弃置/生成的牌数、受伤量、造成伤害量（各"本回合 / 本场战斗"两档） | 不用——读的是游戏自己的记录 |
| 牌堆张数 | 5 | 手牌 / 抽牌堆 / 弃牌堆 / 消耗堆 / 所有牌堆 | 不用 |
| 按条件数牌 | 1 | 五个范围 × **与选牌器同一套多维条件**（六个维度同时生效） | 不用 |
| 自建跟踪 | 4 | 恢复生命的次数与量（各两档） | **要**——游戏没有治疗历史 |

**不收录**"读当前状态"的那些（当前/最大/已损失生命、格挡、能量、星辰、金币、X 值、回合数）：
它们问的是"现在是多少"，不是"发生过几次"。那些在**变量来源模块**里（`Modules/ValueSources/`）。

收成一个模块的价值：这 30 种原来混在取值器的一个大 switch 里与那些状态读数并列，看不出
"哪些是计数"；而"这个工程要不要共享运行时"这类判断当时只能靠 grep 生成器。现在
`CounterCatalog` 是唯一名单（`IsCounter` / `UsesSelfTracked`），显示名也只有一处
（`SourceCatalog.Label` 转调它，与 `VariableModule.PowerPlaceholder` 提供"状态的数值占位符名"同一个做法）。

### 变量来源模块：每个来源一行，读法与名字都只有一处

**要解决的问题**：一个计算型数值要读"变量"（手牌数、状态层数、当前能量…），而这件事在搬进
模块之前是**四份必须互相对得上的名单**：取值器里那段 if/else 加三个 switch 决定怎么读；
`ValueSource.IsPlayerScoped` 里三十三个枚举项决定"要不要取自谁"；schema 里一句
`k == PowerStacks` 决定"要不要再选一个状态"；界面里一个 if 链决定下拉分组。
四份里任何一份漏改都不会报错——只会让某个来源落到兜底分支上**静默读到另一侧的数**，
或者界面上少一个选项。

现在每个来源是**一行声明**（`SourceSpec`）：名字（中英）+ 读法分类 + 取值表达式。
其余判断全部从这一行推出来：

| 读法 | 有哪些 | 取值语句 |
|---|---|---|
| `PlayerScoped` | 当前能量 / 星辰 / 金币 / 回合数 / 两个 X 值 | `var player = …; if (player?.PlayerCombatState is not null) …` |
| `PowerStacks` | 状态层数（要再选是哪个状态） | `powerOwner.GetPower<T>()?.Amount ?? 0` |
| `CreatureStat` | 当前 / 最大 / 已损失生命、格挡 | `who!.CurrentHp`（取自谁由 `Actor` 决定） |
| `Counter` | 计数那 30 种 | 转给计数模块（`CounterEmitter`） |
| `None` | 不取值（固定值） | 变量取 0 |

于是 `IsPlayerScoped` / `NeedsPower` 不再各有一份清单（前者现在是"读法是玩家维度或计数"这一行），
界面的分组与描述里的"自身/目标"也读同一份。

**"获取计算型数值的变量"的五个角色共用同一套读法**：效果数值、重复次数、选牌张数、能量阈值、
星辰阈值——它们以前各自去找取值器，现在都走 `SourceEmitter`，只有结果变量名不同
（`value` / `sourceValue` / `pickCount` / `pickEnergy` / `pickStar`）。`srctest` 用一张卡把这
五个角色全放上，断言同一个来源在五处读出来的是**同一行代码**。

**验收约定**：`SourceCatalog` 的名单必须覆盖枚举的每一个成员——`srctest` 逐个断言，
漏一行会有五条断言同时变红（实测：把"格挡"那一行注释掉，"漏了：Block"立刻现形，
而且能看到它掉进 `None` 分支变成"按 0 处理"）。这一条是照着"四份名单"那个坑定的：
以后加来源，忘了声明读法会被当场拦下，而不是等某张牌的数字算错。


### 多个 mod 共用：adopt-or-host，**不声明依赖**

**要解决的问题**：多个由本编辑器生成的 mod 同时装时，"自建计数"只能有一份账——各记各的
就等于重复实现、重复补丁、重复内存。

**先说为什么不用 `dependencies`**：游戏确实支持 mod 依赖（`ModManifest.dependencies` +
拓扑排序），但那条路有个**硬失败**——依赖缺失时游戏会让依赖它的 mod **整个加载失败**。
而"取用一份共享实现"这件事本来就不该有这种风险。

**做法**：每个用到计数的 mod 的生成物里都带一份**完全相同**的运行时源码，启动时问一句
"该由谁记账"（`SharedRuntime.Adopt()`）：

- 判给自己 → **宿主**：自己装补丁、自己记账、自己算。
- 判给别人 → **不记账**，查询转给那一份（首次调用取一次委托，之后是普通调用）。

于是无论装几个 mod，都是一份记账、一个补丁、一份存储；而且**天然容错**：把宿主那个 mod
删掉或禁用，下次启动剩下的会自动有一个成为宿主。

**宿主的选定与加载顺序无关**：把已加载的候选按**程序集名**排序，最小的当宿主。起初写的是
"谁先调 Adopt 谁当宿主"，那样在"两个程序集都已加载"的情形下会互相找到、**双双变成非宿主**
——计数就永远读到 0，而且不报错（`counttest` 的两 mod 测试就是盯着这件事的）。

**只有带状态的运行时件才需要共享**。这一点值得写清楚，因为它决定了范围：

| 运行时件 | 带状态？ | 结论 |
|---|---|---|
| 计数（`HealTracker`） | **是**（记账） | 共享：先加载的记账，其余转发 |
| 皮肤动画重映射（`AnimationRemap`） | 是，但是**每 mod 自己的**皮肤映射 | 不共享——共享反而会弄坏别的 mod 的皮肤 |
| 伤害槽、永久增伤/重放的两个 Apply 辅助 | 否（只操作传进来的那张牌） | 不共享——各带一份完全无害 |
| 原版牌组件（`CardComponents`） | 是，但**按 mod 前缀天然分账** | 不共享——每个 mod 的补丁只读写自己前缀的 props 条目，同一张卡被两个 mod 各挂组件时两组条目并存、进战斗各应用各的，共享反而要合并分账 |

> 方案阶段我曾把 `AnimationRemap` 也列为"可共享"，核实后发现它的状态属于各自的皮肤映射，
> 共享是**错的**，所以改成每 mod 一份。组件仓库同理：它的"状态"带 mod 前缀隔离，
> 各 mod 一份才是正确形状。

**顺带修的两件事**：

1. **程序集名按工程 id 取唯一名**（`ModForge.<id>`）。原来所有 mod 都叫 `ModForgeGenerated`，
   而它们会被装进**同一个** `AssemblyLoadContext`——同名会造成按名解析的歧义，而"找另一份
   实现"正是按类型名找的。
2. **跨 mod 识别改按方法名**（鸭子类型）。`IPermanentDamageBoost` / `IAddReplay` 必须能被
   卡牌类在**编译期**实现，所以接口只能是每个 mod 一份：于是 mod A 的"永久增伤"遇到 mod B
   的牌时，`card is IPermanentDamageBoost` 是 **false**——明明那张牌有这个能力却认不出来。
   现在两个 Apply 辅助先走同 mod 的接口快路径，认不出时再按**方法名**找一次，跨 mod 也能生效。

**为什么能靠类型名找到对方**：游戏的加载器把 mod 程序集装进同一个进程与同一个
`AssemblyLoadContext`（它自己的 `AssemblyResolve` 只兜 `sts2` 与 `0Harmony`，不影响我们）。
这是这个方案能成立的前提，也是它不依赖任何声明的原因。

**变量模块**要解决的问题是"同一个数值，被五处各自推一遍名字"：声明、取值、升级、等级表、
描述占位符。五处各写一份必然分叉，而且是静默分叉——描述里引用的变量名与卡上实际声明的不
同时，只有游戏内格式化才会失败。所以现在这五处读**同一份规划**（`VariableModule.Slots` /
`RepeatSlots`），文本也只在 `VarSlot` 上写一次。

它回答的是"这个数值由哪三部分构成、占哪个槽"；**不负责**"手牌数怎么数、状态层数怎么取"
——那是变量来源模块（`Modules/ValueSources/SourceEmitter.cs`）的事。两者是分开的：
这一层管"算式长什么样"，那一层管"变量从哪儿读出来"。

`NumericValue` 就是界面上那三格（效果基础值 / 效果变量来源 / 效果变量系数）背后的东西。来源选「无」
时整个式子退化成一个固定值，所以"固定值"与"计算型"不是两种模式，而是同一个式子的两个取值。

变量存在哪里（游戏的 `DynamicVars` 还是生成类的私有字段）是实现细节，语义不受影响：
固定值、以及计算型的伤害/格挡用游戏变量；其它种类的计算型游戏没有对应变量类型，只能写在
生成类的 `_calcBase{n}` / `_calcPerUnit{n}` 字段里，由我们自己发的方法读出来。这两种都由
`VarSlot` 自己给出写法，调用方不需要知道区别（`VarSlot.Storage`）。

**选牌模块**（`Modules/CardPicking/`）要解决的问题是"同一件挑牌的事，九个调用点各拼一遍
字符串"。它按三个决定拆分，组合起来就是界面上那十步流程：

| 决定 | 谁管 | 能看到什么 |
|---|---|---|
| 在哪儿找 | `CardPickCollector` | 此牌 / 全部战斗牌堆 / 某几个牌堆 / 卡组 |
| 按哪一维筛 | `CardPickFilter` | 类型 / 牌名 / 标签 / **关键词** / 稀有度 / 不筛 |
| 怎么取 | `CardPickEmitter` | 全部 / 选择 / 随机 / **至多** |

十步流程整份存在 `CardPick` 上（`Source` / `Piles` / `Dimension` / 五维取值 / `Mode` /
`Count`），**张数也是三件套**（`NumericValue`：基础值 + 变量 × 变量系数），所以
"消耗等于手牌数的一半"写得出来；`CardPickEmitter` 是唯一的出码处，界面与 XML 只是它的两种镜像。
流程二那个列表**空 = 全部战斗牌堆**（游戏的 `PlayerCombatState.AllCards`，含出牌堆——原版
"完美打击"的口径），所以"一个都不勾"与"没写 `<piles>`"是同一件事。

标签与关键词是**两套**（游戏的 `CardTag` 与 `CardKeyword`）：前者是无关行为的元数据
（"这张牌算不算打击牌"），后者是带自动行为的机制标记（消耗、虚无、固有…）。读法也不同
（`c.Tags.Contains(...)` vs `c.Keywords.Contains(...)`），所以流程里它们是并列的两步。
`CardTag` 在游戏里**没有译名**（它不出现在卡面，本地化表里查不到），所以那五个词
（打击 / 防御 / 小刀 / 仆从 / 奥斯提攻击）写在 `GameTerms` 自己的表里。

三条是"照游戏接口用"，不是我们加的判断：

- **"至多 N 张"** 就是 `new CardSelectorPrefs(prompt, 0, N)`——游戏原生支持（原版"净化"
  "守护"用的就是它），构造时会自动让玩家自己确认结束。
- **合法目标不足时全选**也是游戏自己的行为：每个入口都有 `count <= MinSelect` 的提前返回；
  随机那条走 `TakeRandom`，`Take` 天然截断。
- **卡组不能走 `FromCombatPile`**（它对非战斗牌堆抛异常），跨牌堆要走 `FromSimpleGrid`。

跨牌堆**不需要自己做选牌界面**：`FromSimpleGrid` 接受任意牌列表，我们只要拼集合
（`CardPile.GetCards`，原版"窃贼蝗虫"就是这么跨抽牌堆 + 弃牌堆取牌的）。但拼出来的顺序必须
**确定**——那个入口用"索引"在多人之间同步，注释明确要求列表是"确定性生成"的，所以不能按语言排序。

每条效果允许用哪些选项、以及合法性约束（升级只许可升级、变化只许可变化、附魔只许可附魔，
判据用游戏自己的 `CanEnchant` 等 API）由 `CardPickPolicies` **一处定义**，界面、生成器、
导出器、校验器都读它——那份名单以前散在三个文件里且内容不一致。

### 重构期间的两个验证陷阱（都踩过，都已补）

**1. "生成结果逐字节不变"在夹具没覆盖时是空话。** 效果模块搬迁以 `gensnapshot` 的
`diff -r` 为空为门槛。批 1 搬了六种效果（获得能量 / 星辰、消耗牌、三种充能球），
diff 确实为空——但**当时所有夹具一个都没用到这六种**，所以那次对比只证明了"没弄坏另外 25 种"，
对这六种什么都没验证。是事后逐个查覆盖才发现的。

补法：`gensnapshot` 里加了一个 **EffMatrix** 夹具，**每一种效果各来一张牌**（外加"计算型 /
非计算型"的变体，因为两者走不同的模板）。以后每一批都自动受覆盖。

**同一个坑在时机模块上又出现一次**：动手前先查了覆盖，`gensnapshot` 对时机的覆盖是**零**
（`OnPlay` 是默认值，所以连它都没显式出现过）。于是先加了 **TimingMatrix** 夹具——
八种时机、五种牌堆范围、计数器两种归零、自动打出、状态侧四种触发，再动代码。

**2. 夹具能证明"没变"，不能证明"对"。** 所以在 `kindtest`（效果）与 `timingtest`（时机）里
把已搬迁部分的期望写下来（期望值取自**搬迁前的源码**，不是跑一遍新代码抄下来）。
两者互补：夹具防"改坏了别处"，断言防"搬过来就是错的"。

**3. 界面 schema 以前完全没有工具覆盖。** 它是"生成出来的"（界面照着它渲染表单），但改了某个
效果的元数据而漏掉 schema，只会表现为"界面上少一格"，很难发现。现在 `gensnapshot` 也写一份
`_schema.json`（用与编辑器相同的序列化策略），于是"界面长什么样"也能被 diff 对比。

> 关于 `EffectSchemaEntry` 为什么用 camelCase 属性名（与 C# 惯例相反）：这样序列化结果
> **与命名策略无关**，换成 PascalCase 再靠 camelCase 策略去转，就多了一条"策略被改掉就悄悄
> 变样"的隐患。搬迁前它是个匿名对象，字段名本来就是这些。

### 途中修掉的真问题（都有测试钉住）

- **目标候选缺了"其他玩家 / 其他友方"这一族，而且"友方"与"其他"混在一个名字里**
  （用户报的）。原来只有"所有友方 / 随机一名友方"，而"随机一名友方"实际是**不含自己**的
  ——名字说"友方"、集合里却没有自己，与"所有友方含自己"自相矛盾。现在按"**友方含自己、
  其他不含自己**"成对补齐：`AllOtherAllies`（所有其他友方 / 所有其他玩家）、
  `RandomOtherAlly`（随机其他友方 / 随机其他玩家）；"随机一名友方"改成**从全集里抽**
  （含自己，与"随机一名敌人"从全体敌人里抽同一个口径）。玩家轴上原来那个"随机一名友方"
  同样退出候选（它与"随机一名玩家"同集），旧数据照旧按原口径生成、校验器提示改用哪一档。
  "任意其他玩家"就是卡牌目标"任意友方"那一档（游戏的 `AnyAlly` 注释写明排除自己）。

- **「所有友方」把宠物也算进去了**（用户报的）。生成的是 `CombatState.Allies`，而**宠物也在
  `Allies` 里**（`AddCreature` 按 `CombatSide.Player` 放进去；`OstyCmd` 自己就是去 `Allies` 里
  找宠物的）——于是"给所有友方加格挡"会顺手加给奥斯提。原版不是这么做的：原版"所有友方"的牌
  用 `PlayerCreatures`（只含玩家生物，见 `LegionOfBone`），"任意友方"的候选也带 `c.IsPlayer`
  过滤。现在改成 `PlayerCreatures`（**不含宠物**），"随机一名友方"同时**排除自己**（与原版
  一致）。想作用到宠物上得显式选宠物那一档。
- **"作用于其奥斯提"漏了几种效果**（用户报的）：它原来是**每条效果自己声明**"我的句子能不能
  念出对象"，结果只有伤害 / 格挡 / 回复生命 / 施加状态开了，**移除状态、提高 · 降低最大生命、
  失去生命、灾厄判定**这几条（同样作用于生物、同样该能选宠物）没开。现在判据改成**作用域**：
  造物轴的命令都收 `Creature`，宠物就是 `Creature`，所以造物轴一律能配——漏不了。
  配套给那几条补了"对谁"那一半句式（"使目标的奥斯提失去 3 点生命。"），
  顺带修掉一个潜伏的坏句子：**灾厄判定作用于自己**时模板里那个 `{who}` 是空词，
  会念成"立即对执行灾厄判定"（它原来不给"自己"这一档，所以从没暴露）。

- **"作用于其奥斯提"漏了几种效果**（用户报的）：它原来是**每条效果自己声明**"我的句子能不能
  念出对象"，结果只有伤害 / 格挡 / 回复生命 / 施加状态开了，**移除状态、提高 · 降低最大生命、
  失去生命、灾厄判定**这几条（同样作用于生物、同样该能选宠物）没开。现在判据改成**作用域**：
  造物轴的命令都收 `Creature`，宠物就是 `Creature`，所以造物轴一律能配——漏不了。
  配套给那几条补了"对谁"那一半句式（"使目标的奥斯提失去 3 点生命。"），
  顺带修掉一个潜伏的坏句子：**灾厄判定作用于自己**时模板里那个 `{who}` 是空词，
  会念成"立即对执行灾厄判定"（它原来不给"自己"这一档，所以从没暴露）。

- **一张牌上两条"会挑牌"的效果会生成重名的局部变量**（编译不过）。挑牌结果原来一律写进
  `var pickedCards`，而**大多数**挑牌效果都不带后缀（降费 / 免费 / 升级 / 变化 / 搬运 / 复制 /
  附魔 / 增伤），于是"降费 + 升级"这种搭档的卡直接编译失败——已存在的坑，做临时牌集合时
  由新夹具撞出来。现在第二条起自动带卡内编号（第一条仍是 `pickedCards`，所以只有一条挑牌
  效果的卡**一个字节都不变**）。带标签的那几条（消耗 / 丢弃 / 自动打出 / 重放）本来就没问题。
- **"丢弃牌"漏在"会挑牌"的名单外**（`CardPickPolicies.UsesPicker`）。后果有两层：界面上
  它**没有选牌器**（挑哪些牌、挑几张都只能吃模型默认值），而且导出时**不写选牌提示语**——
  可"选择"那一档会弹选择界面，游戏取不到 `selectionScreenPrompt` 会**直接抛异常**。
  也就是说"丢弃牌（选择 1 张）"的卡打出去会崩。名单补上了，`picktest` 也把这份名单
  与生成器对齐（凡是出码真的调选牌器的种类都得在里面）。
- **降费效果会被"数值 ≤ 0 就没用"误报**。那条通用检查假设数值是"量"，而费用增减的数值是
  **带符号的增量**（-1＝便宜 1 点，原版"精密瞄准"就是），于是每一条正常的降费都吃一个警告。
  连同"移除状态可以填 0"一起列进了例外。

- **"随机一名敌人"其实每次都打第一个敌人。** 那一档原来发的是
  `Creature? picked = …HittableEnemies.FirstOrDefault();`——名字叫随机，行为是"取列表第一个"。
  目标模块化时换成游戏自己的随机流（`Rng.CombatTargets.NextItem`，原版 `BouncingFlask`
  取随机目标用的就是它）。这条**改的是生成结果**，`gensnapshot` 的逐字节 diff 里就那几行。
  顺带修掉同一处的重名隐患：两条效果都用随机目标时，局部变量原来都叫 `picked`（编译不过），
  现在带卡内编号（`picked0`），与选牌模块的 `pickedCardsX0` 同一个做法。
- **13 种效果的数值没有三件套（升级被静默丢弃）。** `VariableModule` 只给 11 种效果开变量槽，
  而"有数值"的效果共 **24** 种。没槽的那 13 种（获得能量 / 星辰、回复 / 失去生命、
  复制 / 加入 / 丢弃牌数、三种球、重放、自动打出、费用增减）后果是一条静默失效链：
  生成时把数值写成字面量、**升级增量被丢弃**（升级那段只对"有槽"的效果发语句）、
  描述里写死数字。`tripletest` 现在对全部 24 种逐个断言：有自己的变量、填了升级就有
  `OnUpgrade` 且改的是它自己那个变量、描述用占位符。
  顺带发现游戏**自带** `EnergyVar` / `StarsVar` / `HealVar` / `HpLossVar`，正好补上缺的那四个。
- **X 星的卡编译不过。** 游戏里 `HasEnergyCostX` 是 `protected virtual`，而 `HasStarCostX`
  是 **`public virtual`**（`CardModel.cs:373` / `:467`）——生成器一直按 `protected` 发，
  于是任何 X 星的卡都会报 CS0507。以前**没有任何工具用过 X 星**，所以这个错一直潜伏着：
  界面上勾了 X 星就会生成编译不过的卡。`cardtest` 第一次跑就抓到了。
- **读档后重放次数归零。** 天性重放只写在 `AfterCreated()` 里，而那个钩子**不在读档时调用**
  （读档走 `FromSerializable` → `AfterDeserialized`），而 `BaseReplayCount` 是普通字段、
  不进存档。现在改成 `[SavedProperty]` 自有属性，见「重放」一节。
- **界面上消耗牌的选牌器「没用对」**：`pick` 那十步的投影原本只写在 `EditorSchema.Describe`
  里，而搬进 `Kinds/` 的效果（消耗牌就是其中之一）走的是**另一条路**（行为自己给的
  `EffectSchemaEntry`），于是那条路拿不到 `pick`——界面看见的是"没有选牌器"，退回旧表单。
  现在投影收成 `EditorSchema.WithPick` 一处，**每条**元数据都过一遍（`kindtest` 直接读界面
  收到的 JSON 来钉）。
- **`CardPick.Piles` 的默认值把集合初始化器变成了追加。** 默认给 `[Hand]` 时，
  `Piles = { PileKind.DrawPile }` 得到的是 `[Hand, DrawPile]`（C# 的集合初始化器是往现有列表里
  **追加**），于是"从抽牌堆里挑"会变成"从手牌与抽牌堆里挑"，单牌堆那几档（`FromCombatPile` /
  特殊入口）全都悄悄换成了通用网格。默认改成**空**（= 全部战斗牌堆，本来就是这个字段的语义），
  `InPile` 这类工厂也跟着对了；界面新增效果时仍然默认勾手牌，但那是界面的初值，不写进模型默认值。
- **带维度筛选时描述把「至多 N 张」念成「所有」**：那一支只念条件（"所有攻击牌"），
  而生成的是 `CardSelectorPrefs(prompt, 0, N)`。现在条件 + 流程九/十一起念
  （"至多 1 张攻击牌"/"选择的 2 张打击…"），`kindtest` 按这两种组合钉住。
- **丢弃牌的张数改走选牌器后，`DiscardCount` 那个变量槽忘了摘**：它按 `Amount`（早已不用的字段）
  声明一个永远是 0 的死变量，描述里引用它会显示一个与真正丢弃张数无关的数。已删。
- **"张数"曾经是选牌器私有的一套三件套**（`<pickCount>` + 自己的变量来源），于是"升级后张数 +1"
  写不出来——`EffectUpgrade` 只认数值与次数的增量，而张数既不在数值里、也没有变量槽。
  现在按"每个效果的 base 值即它的基础值"归位：消耗牌的张数就是它的 `<base>`
  （基础值 + 变量 × 变量系数 + 升级增量），选牌器**不再自己处理变量**，只接收变量模块算好的
  那个表达式（`CardPickPolicy.CountFromEffect` + `CardPickEmitter.Lines(..., effectValue)`）。
  顺带把"张数是算出来的"那种情况的描述也修对了：游戏里没有可引用的变量名，所以念不出来源
  就会写出一个看着像真的的数字（"至多 1 张"），现在写成"至多消耗 等于 当前星辰 张牌"。
- **三条球效果（球位 / 生成 / 激发）与召唤的"算出来的"句子会念成基础值。** 它们的 `Describe`
  只渲染固定值那条模板，于是填了变量来源时卡面写的是"生成 1 个闪电充能球"，而实际会生成
  1 + 手牌数 个——与其它计算型效果（"获得 等于手牌数 的能量"）不一致，属于"卡面与代码对不上"。
  **已全部修掉**：三条球效果在批 1、召唤在批 3（各补了 `channelOrbCalc` / `evokeOrbsCalc` /
  `evokeOrbsAllCalc` / `addOrbSlotsCalc` / `summonCalc` 对照句），`phrasetest` 与 `gensnapshot`
  里各补了对应的对照行/夹具——**没有夹具的那一支等于没验**，所以两处都补。
- **英文球名与 "Orb" 之间少一个空格**（"FrostOrb"）。连接由句式表的 `orbJoinSuffix` 给
  （中文空、英文一个空格），不在代码里判语言；没有游戏目录时球名退回**枚举名**
  （不再退回"充能球/Orb"那种词——模板后面还要再补一次后缀，会印成"充能球充能球"）。
- **不挑牌的效果也带了一段没有作用的 `<pick>`，导出时还多写一条读不到的提示语。**
  两处原因：界面给每条新效果都塞了一份选牌配置（`piles=[Hand]` 不是模型默认的空），
  而 `pickForm` 与数值区的显隐判断顺手把这个字段建了出来（`pickOf` 是懒建的）；
  导出器判"要不要写提示语"时只看 `UsesPrompt`，而不挑牌的种类都落在策略的默认分支上
  （`UsesPrompt: true`）。后者的**实际危害**是提示语按第一条匹配的效果取词：一张
  "先获得能量、再消耗牌（选择 1 张）"的卡，提示语会退化成通用的"选择若干张牌"。
  现在：界面只给 `meta.pick` 存在的种类配 pick、换成不挑牌的种类时丢掉、取 pick 之前先看策略；
  导出器改用 `OpensChooser`（`UsesPicker` × `UsesPrompt` × 流程九=选择）。`filetest` 与
  `picktest` 各钉一条（后者真的导出一张"不挑牌 + 会弹界面"的卡，核对提示语归属）。

### 已知缺口（结构重构时特意保留，不改行为）

- `EffectResolver.DynamicVars()` 把"变量系数"截成整数（`(int)Source.PerUnit`），所以界面上
  预览"变量系数"填了小数（如 0.5）时会看到偏差。改它会让生成的预览值变化，属于行为改动，
  单独一轮处理。
- 编辑器界面里 `ui/app.js` 判断某个来源要不要填"状态"时读的是 `k.powerType`，而后端 schema
  给的是 `needsPower`——两处名字不一致。
- `EditorSchema.Describe` 里有个 `hasPermanent` 标志，发出去了但从来没被置为 `true`。
- **没有任何自定义状态的工程编译不过**：生成的卡无条件写 `using <id>.Generated.Powers;`，
  而那个命名空间只在工程里有状态时才存在。界面新建的工程默认就是零状态，所以这条会真实撞上
  （走 `picktest` 时暴露的）。修法是一行——有这个命名空间时才发那行 using——但它会改变
  零状态工程的生成结果，所以留到单独一轮。
- **"作用于牌"那一轴（消耗牌这类）还没有玩家目标**。用户提的是"消耗牌的目标虽然是牌，
  但也有个隐形目标——玩家"，也就是"让所有玩家各消耗一张"。这件事**动物很小**（选牌模块本来就
  按玩家参数化：`CardPickCollector.CardList(pick, player)` 收的就是玩家表达式）。当初要等
  批 5/6 重写那 12 处出码路径，现在搬迁已完成、那些调用点都在各自的 `Kinds/` 文件里——
  这条成了目标模块上剩下的最后一个已知缺口，随时可做：界面给"作用于牌"轴加玩家档，
  出码把玩家表达式一路传进选牌器即可。
- **其余会挑牌的效果还没归到"base 即张数"上**（升级 / 变化 / 搬运 / 附魔 / 复制 / 增伤 / 重放 /
  降费 / 免费 / 自动打出）：它们的数值另有含义（复制几份、附几层、打几次…），所以张数仍写在
  `<pickCount>` 那一格。等各自整理时再逐条搬过去——搬过去之后升级改张数、张数是算出来的
  都会自动成立。消耗牌已经搬完，可以作为样板。
- **召唤（批 3）也有"算出来的数值只念基础值"这条毛病**（与三条球效果当初一样：填了变量来源时
  卡面会写"召唤 1。"，而实际数值是 1 + 手牌数）。**批 3 已修**：补了 `summonCalc` 句式，
  句子改由 `SummonBehavior` 自己出（它不再是"提前返回"的那一支，所以 `AddCalculationVars`
  正常被调到），并加了 `FX_SUMMON_CALC` 夹具与 `phrasetest` 对照行。

编辑器运行时会建立这些目录。工程是**独立文件夹**（见上节），放在 `projects/` 下；
其余是程序自己用的缓存与设置：

```
settings.json   程序默认路径（界面上可改）
projects/       默认的项目父目录，每个项目一个文件夹
  <项目名>/     工程文件夹本身（About / Language / Create / Cards / …）
cardart/        素材库：你自己攒图的地方，编辑器只读
presenter/      游戏卡面素材缓存（可重建）
data/           卡牌数据快照等缓存（可重建）
build/          缓存目录（导出产物现在写在工程的 Mod/ 里）
```

工程里生成源码的那个文件夹叫 `Source/` 而不是 `src`：程序自己的 C# 源码树叫 `src/`，而工程
默认就紧挨着它，生成物若也叫 `src` 就会混进去（实测踩过）。

项目里的卡图引用存的是**相对于项目 `cardart` 的路径**，不是绝对路径——否则移动项目文件夹后
卡图会全部失效。更早的版本把工程直接摊在程序根目录、产物放在 `%APPDATA%\ModForge`，
两种情况首次启动都会自动迁进工程文件夹（只复制、不删除），并改写卡图引用。

`docs/platform-notes.md` 是格式相关的参考：PCK 与 .ctex 的布局、ModelId 规则、mod 加载顺序、游戏请求的动画槽位名，以及若干设计决策的理由。

## 工具

每个工具回答一个问题，可单独运行（消息为中文）：

| 工具 | 用途 |
|---|---|
| `forge` | 跑完整流水线并校验结果 |
| `verify` | 建立原版内容目录；校验一个 mod 程序集 |
| `battest` | 检查 `.bat` 脚本的换行与 BOM——cmd.exe 对裸 LF 的解析会错乱，且症状完全不像换行问题 |
| `effecttest` | 确认卡牌数值由效果推导，且共享效果在卡牌与状态中都生效 |
| `sharedgen` | 打印「共享效果被卡牌与状态同时使用」的生成代码 |
| `newfx` | 验证计算型数值、牌堆操作与触发时机（含中英描述） |

## 原版能力审计（`cardaudit`）

要回答的是"我们能不能做原版做过的事"，所以先得知道每张原版卡**实际做了什么**——描述文本只是占位符，真正行为在代码里。

审计分两层取数据，各取所长：

| 层 | 来源 | 取什么 |
|---|---|---|
| 是什么 | `CardStatsReader` 读 IL | 费用 / 类型 / 稀有度 / 目标 / 数值 / 升级（已由 `statstest` 逐字段验证） |
| 做什么 | 扫 `decompiled/` 源码 | 实际调用的命令、覆写的钩子、计算型数值的来源 |

第二层扫源码而不是再写一套字节码解释器：数值那部分已经有验证过的 IL 读取，而"调了哪些命令"用源码看得清、规则也写在明处（`tools/cardaudit/Mechanics.cs`）。代价是这一步依赖 `decompiled/` 目录，所以它是**开发期工具**，不是运行时依赖。

扫的时候要**跟两层**：卡牌类 → 它施加的状态类。能力牌的真实行为在状态类里，只扫卡牌类会把整类能力牌判成可实现（详见「分批核对进度」里那一节的说明）。

每张卡给一个结论：

| 结论 | 含义 |
|---|---|
| 可直接实现 | 现有效果就能照搬 |
| 实现方式不同 | 能做，但原版走的是我们表达不了的路径（多半是额外钩子，得改写成状态） |
| 可能实现错误 | 能做，但映射有歧义，可能选错语义 |
| 无法实现 | 用到了我们完全没有的操作，得先加效果 |
| 无需实现 | 废牌 / 纯关键词牌 |

产出两份：

- `data/card-audit.json` —— 完整数据，供程序或后续工具使用
- `data/card-audit.md` —— 按「牌池 → 稀有度」分组的核对清单，开头有**批次总表**（每个批次各档多少张），用来决定先核对哪批；另有「我们缺的操作」与「可能实现错误的映射」两份汇总

```bash
cd tools/cardaudit && dotnet run
```

工具自带**已知卡自检**：用 15 张行为确定的卡校对识别规则（打击、痛击、放血、全身撞击、灰烬打击、子弹时间、开悟、轰击、爪击、剑柄打击、神化、冲锋！！、降灵、挖掘、头槌），规则被改坏会立刻失败。这不是多余的——识别靠正则，最危险的错误是"以为认出来了、其实认错了"，而那种错会让整份报告不可信。

#### 一个必须说清的方法修正：能力牌要跟进状态类

审计最初只扫**卡牌类**，于是所有能力牌都只看到一句 `PowerCmd.Apply<XPower>`——报告说"施加一个状态，能实现"，而卡的真实行为（"每消耗一张牌抽一张""每获得格挡造成伤害"）全写在**状态类**里。等于把整类能力牌判成了可实现。

现在卡类扫完会跟进它施加的每个状态类，把状态覆写、而我们表达不了的钩子并进结论（报告里标注"来自状态 X"）。修正后"可直接实现"从 501 降到 362、"实现方式不同"从 8 涨到 147——**这不是退步，是原来的数字虚高**。

顺带确认了我们的状态能发出哪些钩子，与游戏的状态钩子对照后，缺口集中在三类（按卡住的卡数排）：

| 缺的状态钩子 | 卡住的卡数 | 用途 |
|---|---:|---|
| `BeforeCardPlayed` | 18 | 常与 `AfterCardPlayed` 成对，用来"在牌结算前记下它" |
| `AfterEnergyReset` | 14 | 回合开始能量重置时 |
| `AfterApplied` | 11 | 状态刚被施加时（"肉盾"给队友加守护、"壁垒"改格挡是否消失） |
| `ModifyHandDraw` / `BeforeHandDraw` | 9 / 8 | 改抽牌数、抽牌前 |
| `BeforeSideTurnEnd` | 8 | 回合结束**之前**（我们的 `AfterSideTurnEnd` 在弃手牌之后） |
| `ModifyBlockAdditive` / `ModifyBlockMultiplicative` | 6 / 1 | 改格挡数值（"坚定不移"翻倍首次格挡） |
| `AfterBlockGained` | 1 | 获得格挡时（"势不可当"） |

这些是后续要补的状态时机，优先级按卡住的卡数。注意 `AfterApplied` 有真有假：有的状态（"肉盾"）在其中做真事，有的（"壁垒"）只是存个显示用的名字——要不要补它取决于前者值不值得。

第一批（ironclad 基础牌与普通牌）核对时发现 2 张缺能力，补上后**全部 23 张都能实现**：

- **头槌**：造成伤害后，把弃牌堆里选中的一张牌放到抽牌堆顶 → 补了「在牌堆间移动牌」。
- **完美打击**：伤害按"名字里有『打击』的牌有几张"计算 → 补了「按条件数牌」这个数值来源。

关于完美打击有一点值得记下来：中文描述写的是"名字中含有『打击』的牌"，但**代码里判的是卡牌标签**（`c.Tags.Contains(CardTag.Strike)`），不是名字。按名字判反而不可靠——改名或换语言就失效。所以编辑器里的条件是"打击牌（按标签）"。

第二批（ironclad 进阶牌）最初有一张做不到，**踩踏**：

> 对所有敌人造成 12 点伤害。你在本回合中每打出过一张攻击牌，其耗能减少 1。

它覆写 `AfterCardEnteredCombat` + `BeforeCardPlayed`，反应的是"你打出的任意一张攻击牌"——而当时我们的效果只作用在此牌的时机上，"别的牌被打出时让我降价"表达不了。这是"实现方式不同"里最典型的一类。

**后来为它补了「打出一张牌时」这个时机**（见「触发时机」一节），于是同一批卡里的这一类全都落地了：踩踏、精密瞄准、女妖之嚎（关键词筛选）、如此甚好（计数器）。按当时的统计口径，可直接实现数从 35 升到 36。

（后来那个数字被上面说的「跟进状态类」修正覆盖了——现在这一批是 27/36，差的 9 张全是能力牌，与「打出一张牌时」无关。）

核对时还确认了四件事，都已写进审计的判定规则：

- **"只对自己生效"的钩子不算做不到。** 原版触发自身时也用 `AfterCardPlayed` / `AfterCardExhausted`，而我们本来就会为对应的时机发出同名钩子（"被消耗时""抽到时""自动打出 → 此牌"）。不区分的话，彼岸咆哮、战鼓、以及"回合结束时若在手牌中"那一整类诅咒牌都会被误报成做不到（实测误报 19 张）。
- **"反应任意一张牌"的钩子现在也不算做不到。** `AfterCardPlayed` / `AfterCardPlayedLate` / `BeforeCardPlayed` 的任意牌用法已由「打出一张牌时」覆盖，审计把它们记进报告但不计入阻塞项。
- **能覆盖但有已知差异的要单独说明**，不当作"等价"。目前有三处：
  - `AfterCardEnteredCombat`：原版用它补算"这张牌是战斗中生成的"那种情况，我们从进入牌堆那刻起算，会少算之前的张数。
  - `BeforeSideTurnStart` / `AfterPlayerTurnStart`：引擎的回合开始其实是三个钩子（`BeforeSideTurnStart` → 抽牌 → `AfterPlayerTurnStart` → `AfterSideTurnStart`），我们只发最后那个，所以"回合开始时"的效果落在抽牌**之后**。对"从弃牌堆取一张牌再升级"这种结果相同（弃手牌发生在上一回合结束时），差别只在"与抽牌的先后"——写进报告让人知道往哪个方向偏。
- **纯表现层的钩子不算做不到。** 例如"燃烧"唯一的钩子 `OnEnqueuePlayVfx` 只是播一团火；我们的卡不生成入场特效，但照样能用。

第三批（ironclad 稀有牌，26 张）18/26 可直接实现，是「跟进状态类」修正后的第一批数据：

> **好勇斗狠**：在你的回合开始时，将你弃牌堆的一张随机攻击牌放入你的手牌并将其升级。

这张归入"可直接实现"是因为它走 `BeforeSideTurnStart`，而我们上面记了差异：我们在抽牌之后。**对这张的结果完全一样**——弃手牌发生在上一回合结束时，那时牌已经在弃牌堆里了，抽牌不会改变弃牌堆。所以它可以用「状态 + 回合开始时 + 随机 1 张攻击牌 → 移到手牌 → 升级」拼出来。

这一批里有 2 张当时缺能力，**后来都补上了**：

> **狂宴**：造成 10 点伤害。斩杀时，永久获得 3 点最大生命值。

补了「提高最大生命」（见「提高 / 降低最大生命」一节）。这个效果本身不复杂，值得记的是它**不需要**存档支持——动的是玩家自己的最大生命值，跨战斗自然保留，与"永久增伤"那种要靠 `SavedProperty` 的情况不同。

> **扯碎**：造成 5 点伤害。在本场战斗中，你每失去过一次生命值，这张牌就额外造成一次伤害。

这一张同时要两样新东西：**计算型的重复打出次数**（伤害固定、次数才算）与**"失去生命的次数"这个来源**。它的样子正好说明为什么次数不能借用数值的来源——伤害是 5、次数基础值是 1，两个基础值不同，共用一套就写不出来。

其余 8 张是能力牌，行为在状态类里，缺的都是状态钩子（见上一节那张表）：壁垒（`ShouldClearBlock`）、黑暗之拥（`AfterCardExhausted`）、地狱狂徒（`AfterCardDrawnEarly` + `BeforeAttack`）、势不可当（`AfterBlockGained`）、连环拳（`ModifyCardPlayCount`）、薪火之源（`ModifyMaxEnergy`）、肉盾（`AfterApplied`）、坚定不移（`ModifyBlockMultiplicative`）。

这一批的结论很清楚：**下一步该补的是状态（PowerDef）的触发时机**，而不是卡牌效果。卡牌的时机已经够用了。

### 已知的映射陷阱

识别过程中确认了几处"看着像、其实不是"的地方，记在这里免得以后重新踩：

- **失去生命 ≠ 造成伤害。** 两者在游戏里都走 `CreatureCmd.Damage`，区分方式是**读哪个数值变量**：`DynamicVars.HpLoss` 是失去生命（不受格挡、不受增伤），`DynamicVars.Damage` 才是伤害。我们这边是两条不同的效果（`LoseHp` / `DealDamage`），映射错了行为就不同。
- **免费 ≠ 降费。** 免费走 `CardModel.SetToFree*`（能量与星辰一起清 0），降费走 `CardEnergyCost.Add*`（只碰能量）。
- **自增伤不走 Cmd。** 爪击 / 撕咬是直接改 `DynamicVars.Damage.BaseValue`，按"调用了哪些命令"是抓不到的，得单独认。
- **"此牌"还是"牌堆里的牌"**：`CardCmd.AutoPlay` / `Exhaust` / `CardPileCmd.Add` 都两种都会出现，按实参区分（`this` 是自己，变量名是别的牌，`null` 只是目标不是被派出的牌）。
- **"搬运一张已有的牌"我们做不到。** `CardPileCmd.Add(x, 某牌堆)` 里 `x` 是 `this` 时是"把这张牌放进某牌堆"（我们支持 `MoveThisCardToPile`），是别的牌时是"把任意一张已有的牌在两堆之间搬运"——**这条我们没有**（原版"头槌""万事通"用它）。这个区分不做的话会把缺的能力误报成"能实现"。
- **数值来源不只是"整堆计数"。** 除了整堆张数、状态层数、生物属性、玩家资源，原版还用**按条件数牌**（`Count(c => …)`）与**按战斗历史计数**（战斗历史里的条目数）。这两类现在都支持：条件数牌用**与选牌器同一套多维筛选**（稀有度 / 类型 / 标签 / 关键词 / 牌 ID / 两个费用维度），所以原版那几条扁平条件都覆盖得到；历史计数只支持"打牌数 / 抽牌数 / 失去生命次数"这几类**条目**。识别时要把超出的部分报出来，否则同样会把缺的能力误报成"能实现"。
- **能力牌的钩子在状态类里，不在卡牌类里。** 审计必须跟两层（卡牌类 → 它施加的状态类），否则整类能力牌会被判成"施加一个状态，能实现"——"黑暗之拥"（每消耗一张牌抽一张）就是这样被漏掉过的。
- **共享效果合并要整体复制，不能逐字段抄。** `EffectResolver.Merge` 曾经逐字段抄一份新对象，于是每加一个新属性都得记得在那边补一行；漏掉的那一项（作用条件、关键词筛选、计算型次数…）会**静默失效**：编译正常，只是行为不是设的那样，而且只在使用共享效果时出现。现在改成 `EffectDef.Clone()` + 只换升级增量，`sharedgen` 有一张卡专门盯这件事（故意用旧写法会立刻失败）。
- **`Calculated` / `Repeat` 不是阻塞项。** 这两个标记只说明这张卡用了计算型数值或重复次数，而那两样我们都支持——不排除掉会把一批本来能直接实现的卡（全身撞击、飞剑回旋镖）误判成"实现方式不同"。

## 扩展方式

- **新增效果种类**：在 `EffectKind` 里加一项，在 `EffectEmitter` 里映射，再在 `EditorSchema` 里加个选项。界面表单由该 schema 生成，所以不用改界面代码，共享效果也会自动支持新种类。
- **新增效果的说法**：只需在 `language/sentences/*.json` 的 `templates` 里加一条；若该说法只对某些效果有（如牌堆操作），还要把效果种类指到新模板名——30 种效果的句子都在各自文件里（`Kinds/<X>Behavior.cs`）。模板名写错或漏加都**不会报错**——会退回 `unknown` 那条通用句子，占位符还都能填上，于是输出看起来是正常的一句话，只是意思不对。`phrasetest` 会遍历所有效果形状、断言没有模板没找到，所以这种情况会在测试里现形。新增用词（如某个来源的名字）或某个枚举值的说法时同理，还要把它加进 `DescriptionModule.RequiredWordKeys()`；**注意 `EffectDescribe.Word()` 只查 words 段**——把短词写进 sentences 段再从 `Word()` 取，会静默取到空串（实测踩过，兜底词要改成 `Render()` 取）。
- **新增状态触发时机**：在 `PowerTrigger` 里加一项，并在 `CodeGenerator.GeneratePower` 里发出对应钩子。可用的钩子名见 `docs/platform-notes.md`。
- **新增内容类型**（遗物、药水）：内容目录已经能读到它们，剩下的是生成器与校验，照着卡牌做即可。
- **新增效果出现的位置**：卡牌与状态都通过 `EffectResolver` 解析，所以第三种位置（比如遗物触发）只需要展开自己的效果列表，并用合适的 `EmitContext` 发出代码。
